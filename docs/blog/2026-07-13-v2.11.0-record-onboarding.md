# AI가 '완료했다'고 말하기 전에, repo가 먼저 따진다 — VHK v2.11.0

> 도구 자랑이 아니라, AI 코딩에서 계속 새는 두 곳에 관한 이야기다. v2.11.0은 그 둘을 repo 안 게이트로 막았다.

## 새는 곳 하나 — 새 프로젝트 첫걸음이 막막하다

`vhk init`으로 프로젝트 뼈대를 만들면 `docs/PRD.md`, `docs/ARCHITECTURE.md` 같은 문서가 생긴다. 그런데 열어보면 빈칸에 `**FILL**`이라고 적혀 있었다. 개발자면 "아 여기 채우라는 거구나" 하겠지만, 비개발자에겐 암호다. **뭘 채워야 할지 모른 채 첫 화면에서 막힌다.**

v2.11.0은 그 빈칸을 질문으로 바꿨다.

```bash
$ vhk init -y --name demo --type webapp
✅ 규칙 파생 완료 — AGENTS.md 등 도구별 규칙 파일 생성
📋 설치 점검 — 다 준비됐는지 확인했어요
  규칙 파일    9/9개 연결됨 ✅   (.cursorrules·AGENTS.md·CLAUDE.md 등 도구별 규칙 파일)
  기록 폴더    5/5종 만들어짐 ✅
  첫 인터뷰    다음 세션 시작 때 자동으로 시작돼요 (도메인 규칙 + 기획 슬롯)
```

이제 PRD를 열면 `**FILL**` 대신 이렇게 적혀 있다:

```
## 문제 (Problem)
[여기에 작성: 어떤 불편·문제를 푸나 (지금은 어떻게 해결 중인지도)]
```

- **채울 자리가 질문이다.** 신청서 빈칸의 안내 문구처럼, 뭘 적어야 할지 그 자리에서 읽힌다.
- **문서가 스스로 진행률을 센다.** `vhk check`가 "📝 미완성 슬롯 13개 — docs/PRD.md 9 · docs/ARCHITECTURE.md 4"라고 알려준다. 채울수록 숫자가 준다.
- **AI가 대신 채우되 지어내지 않는다.** 첫 세션에서 AI가 "이 칸은 사용자 답변으로만 채워라 — 추측 금지"라는 지시를 받고 인터뷰로 채운다. 못 얻은 칸은 마커로 남긴다.
- **`AGENTS.md`가 바로 생긴다.** init이 규칙 파일을 즉시 파생해서, Codex·Zed 같은 다른 에이전트도 첫 세션부터 프로젝트 규칙을 본다.

> ⚠️ 한 가지 짚을 것 — **첫 세션 인터뷰의 "자동 시작"은 Claude Code에서만 자동이다.** SessionStart 훅이 Claude Code 고유 기능이라, Cursor·Codex 등은 규칙 파일에 심긴 문구로 수동 트리거만 받는다. VHK의 실행 계층(규칙·기록·게이트)은 도구를 안 가리지만, "스스로 깨우는" 트리거는 아직 Claude Code에 기댄다. 이건 우리 RFC에 "격차 축소지 소멸 아님"으로 적어둔, 알고 있는 공백이다.

## 새는 곳 둘 — AI가 뭘 왜 바꿨는지 기록이 증발한다

AI가 코드를 왕창 고치고 "완료했어요"라며 커밋한다. 3주 뒤, 왜 이렇게 짰는지 아무도 모른다. 기록은 "나중에 하자"가 되고, 대개 안 한다.

v2.11.0은 이걸 **커밋 시점에** 막는다. git 저장소에서 `vhk init`을 하면 git `commit-msg` 훅이 심겨서, **세션 일지 없는 코드 커밋을 차단**한다.

```bash
$ echo "export const x = 1" > src/foo.ts
$ git add -A && git commit -m "feat: add foo"

[record-check BLOCK] 실질 코드변경 1건이 스테이지됐는데 오늘 세션일지(docs/log/2026-07-13-*.md)가 스테이지되지 않았습니다.
  - src/foo.ts
AI 작업지시: ① docs/log/2026-07-13-<작업명>.md 에 이 세션의 작업 내역을 기록 ② git add 로 스테이지 ③ 커밋 재시도. 사소·문서성 변경이면 커밋 메시지에 [skip-record] 를 넣어 우회하세요.

# → 커밋 안 됨. 일지를 쓰거나 [skip-record]를 넣어야 통과.
```

- **차단 메시지가 잔소리가 아니라 AI 작업지시서다.** 바이브코딩에서 커밋 버튼은 AI가 누른다. 그러니 사람은 신경 쓸 게 없다 — 일지 작성과 재커밋을 AI가 처리한다.
- **git 훅이라 도구를 안 가린다.** Claude Code·Cursor·Codex 어디서 커밋해도 git이 실행한다. (이건 VHK만의 특성이 아니라 git 훅을 쓰는 도구—husky·lefthook 포함—의 공통 속성이다.)
- **설정이 필요 없다.** `vhk init`이 훅을 자동으로 심는다. 별도 패키지 설치나 설정 파일이 없다. 단, 이미 husky·lefthook을 쓰는 팀은 git이 `.git/hooks`를 무시하므로 — VHK가 거짓으로 "배선 완료"를 찍는 대신 "미배선 + 수동 통합 안내"를 띄운다. 그 경우 훅 한 줄을 직접 넣어야 기록 집행이 켜진다.
- **LLM 판단이 아니라 결정적 규칙이다.** "스테이지에 오늘자 일지 파일이 있나 없나" — 휴리스틱이 아니라 파일 존재 여부라 오탐이 적다.

## 이 둘은 기존 검증과 한 벌이다

기록 온보딩과 기록 집행은 완전히 새로 만든 게 아니라, 이전부터 있던 완료 검증의 **앞단을 채우는** 쪽에 가깝다. `vhk receipt`(v2.11.0 신규 아님)는 "완료했다"는 자기보고를 안 믿고 기계 증거(종료코드·git dirty·SHA)로 대조해왔다. 이번 두 기능이 그 검증에 "기록"이라는 재료를 확실히 공급한다.

```bash
$ vhk receipt

🧾 증거 영수증 (receipt)
  판정: 🔴 BLOCK
   • working tree 가 dirty — 미커밋/untracked 변경 있음
  ⚠️  이 영수증은 게으른 거짓완료(빌드 깨짐·미커밋·낡은 증거)를 잡지, 미묘한 오류(그럴듯하게
      틀린 코드)는 못 잡는다. 판정은 기계증거 기반이며 LLM 추론이 아니다.
  🔴 기계증거가 "됐어요"와 모순 — 아직 완료 아님.
```

여기서 중요한 건 마지막 경고다. 영수증이 **자기가 무엇을 못 잡는지 먼저 밝힌다** — "미묘한 오류는 못 잡는다"고. 과대광고 대신 게이트의 한계를 먼저 적는다.

## 정직한 경계

감사층을 자처하는 도구가 자기 한계를 숨기면 그 순간 감사층이 아니다. 그래서 이 게이트가 **막지 않는 것**과 **하지 못하는 것**을 나눠서 적는다.

**의도적으로 막지 않는 것** (과잉 차단 방지)

- merge·pull·cherry-pick·revert·rebase는 통과 — 병합엔 새 일지가 없는 게 정상이다.
- 사소·문서성 커밋은 `[skip-record]`로 우회 — 실질 코드변경만 잡는다.
- node가 없거나 게이트 자체에 결함이 있으면 fail-open — 도구의 버그가 사용자의 커밋을 막지 않는다.

**아직 못 푸는 것** (진짜 한계 — 알고 있고, 문서에도 적어뒀다)

- **`git commit --no-verify`면 통째로 우회된다.** git 훅의 원천 한계라 우리가 막을 수 없다. 유일한 백스톱은 세션 종료 때 `vhk work handoff`가 미기록 후보를 다시 훑는 것 — 그마저도 handoff를 실제로 실행해야 작동한다. 완전 차단이 아니라 마찰을 거는 것에 가깝다.
- **일지의 "내용"은 검증하지 않는다.** 게이트가 보는 건 "오늘/어제 날짜의 `docs/log/*.md` 파일이 스테이지에 있나"뿐이다. 빈 파일이든 "작업함" 한 줄이든 통과한다. 존재를 강제할 뿐, 진실성은 못 본다(그건 결정적 검사로 불가능한 영역이라 의도적으로 안 한다).
- **첫 세션 자동 온보딩은 Claude Code에서만 자동이다.** (위 온보딩 섹션 각주 참조) — 다른 에이전트는 아직 수동이다.

무엇을 막고 무엇을 흘려보낼지 — 이 경계 판단들은 적대검증 2라운드에서 "merge 차단 지옥·amend 오판·husky 거짓 성공"을 실제로 잡아 고친 결과다. 반대로 "못 푸는 것"은 우리 RFC에 이미 같은 문장으로 적혀 있다 — 마케팅 글이라고 빼지 않았다.

## 한 줄로

VHK는 특정 AI 에이전트를 대체하지 않는다. **어떤 AI 위에 얹혀서, AI가 뭘 했는지 검증하고 기록을 강제하는 층**이다 — 한마디로 '반증 가능한 감사·거버넌스 층'. v2.11.0은 그 층을 두 곳에서 더 촘촘하게 했다 — 시작할 때(온보딩)와 커밋할 때(기록 집행).

