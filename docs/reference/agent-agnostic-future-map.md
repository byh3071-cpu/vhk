# 에이전트 비종속 생태계 — 미래 설계 지도

> 상태: **참고 지도. 현재 기능·승인된 계약·구현 로드맵이 아니다.**
>
> 목적: 대화에서 나온 장기 의도를 잃지 않되, RFC 0064의 작은 읽기 전용 범위와 섞지 않는다.

## 1. 한눈에 보기

```text
DISCOVER
Yohan Inbox · 모바일 캡처 · 리서치 · 자유 대화
                         │
                         │ 만들기로 결정
                         ▼
DEFINE / EXECUTE / VERIFY
VHK Core — 프로젝트 안의 작업 실행과 검증
                         │
              ┌──────────┴──────────┐
              ▼                     ▼
Yohan Control Tower             Yohan MCP
사람이 보고·결정·승인             AI가 읽고·행동·기록
              │                     │
              └──────────┬──────────┘
                         ▼
       Yohan Brain · Git · Calendar · 외부 서비스
```

가장 짧은 역할 구분:

- **Yohan Inbox:** 모바일에서 자료를 바로 넣는 입구
- **VHK Core:** 만들기로 한 프로젝트를 정의·실행·검증하는 범용 하네스
- **Yohan Control Tower:** 사람이 전체 프로젝트와 승인을 보는 단일 관제 지점
- **Yohan MCP:** AI 에이전트가 같은 업무 의미로 읽고 행동하는 인터페이스
- **Yohan Brain:** 프로젝트를 넘는 장기 지식·결정·패턴
- **Git:** 코드, 프로젝트 문서와 이식 가능한 검증 자산
- **Calendar:** Task를 실제 시간에 배치하는 외부 시간 원본

VHK Core는 개인 통합 레이어를 몰라야 한다. 개인 통합 레이어는 VHK Core의 공개 계약을 사용할 수 있다.

## 2. 공통 원칙

1. **앱을 전부 다시 만들지 않는다.** 데이터 모델, 맥락 조립, 상태 전이와 AI 인터페이스를 소유한다.
2. **정보 종류마다 원본 하나를 정한다.** 같은 값을 여러 앱에서 동시에 수정하지 않는다.
3. **사람 진입점과 AI 진입점을 분리한다.** 사람은 관제탑, AI는 MCP를 사용한다.
4. **원문과 정제 결과를 구분한다.** 원문을 지우지 않고 처리 상태와 산출물을 연결한다.
5. **보이지 않는 자동화는 증거를 남긴다.** 무엇을 읽고 왜 분류했는지 확인 가능해야 한다.
6. **읽기부터 검증한 뒤 쓴다.** 검색·투영이 정확한지 확인하기 전 상태 쓰기나 자동 완료를 열지 않는다.
7. **하나의 실행 루프만 완료를 판정한다.** 에이전트 수와 상관없이 권한자는 하나다.
8. **자동화는 반복이 입증된 뒤 추가한다.** 한 번의 취향을 공통 Rule이나 Skill로 승격하지 않는다.

## 3. 정보 수집과 Yohan Inbox

### 보존할 의도

- Instagram, Threads, X, YouTube, Telegram, 웹 링크, 이미지와 텍스트를 모바일에서 바로 넣는다.
- 모바일 캡처는 Yohan MCP를 중간 홉으로 요구하지 않고 Yohan Inbox에 직접 들어간다. MCP는 AI가 처리할 때 쓰는 입구다.
- 집 PC에 돌아와 다시 복사하는 중간 병목을 없앤다.
- “저장만 하고 쌓임”을 막고, 자료를 실제 지식·Skill·Task·콘텐츠·폐기로 결정한다.
- 현재 쌓인 항목은 삭제 리셋이 아니라 **미처리 0**을 목표로 정리한다.
- 기존 Telegram bot과 Yohan Brain ingestion 자산은 재사용 가능성을 먼저 본다.

### 구체적인 수집 출처

| 출처 | 놓치지 말아야 할 원문 |
|---|---|
| Instagram 리포스트·북마크 | URL, 본문, 작성자, 이미지 전체. carousel은 2장 이후도 장수와 순서를 보존 |
| Threads 리포스트 | URL, 본문, 연결된 글 흐름과 첨부 이미지 |
| X 리포스트·북마크 | URL, 본문, 인용·스레드 관계와 첨부 미디어 |
| YouTube | URL, 제목, 채널, 자막. NotebookLM 투입 또는 나중에 볼 동영상 상태와 연결 |
| Telegram·웹 공유 | 원 메시지·URL·첨부 파일과 공유 시점 |
| 직접 촬영·스크린샷·텍스트 | 이미지 원본, 이미지 묶음 순서, 직접 입력한 메모 |

초기 관심 분류는 **AI 최신 트렌드·정보·지식, AI Skill·Plugin·GitHub 오픈소스, 디자인,
재무, 투자, 기타**다. 이는 검색과 1차 분류를 위한 시작점이며, 분류 체계를 먼저 크게 만들지
않는다. 실제 적체 처리에서 반복되는 항목만 합치거나 세분화한다.

가능한 결과는 보관용 요약에 그치지 않는다. 지식·Skill·Task 외에도 정보 공유 글, 카드뉴스,
그리고 **댓글 키워드에 반응해 요청 자료를 메시지로 전달하는 콘텐츠 흐름**이 후보가 될 수 있다.
다만 댓글·메시지 자동화는 플랫폼 정책, 수신 동의, 계정 안전과 사람 승인 경계를 확인한 뒤 별도
자동화로 연다.

### 권장 처리 흐름

```text
Capture
원문·URL·플랫폼·캡처 시각을 그대로 저장
   ▼
Acquire
링크 본문, 이미지 묶음, 자막을 가능한 방식으로 확보
   ▼
Understand
OCR·구조 추출·요약, 신뢰도와 누락 표시
   ▼
Decide
폐기 / 보관 / 지식 / Skill 후보 / Task / 콘텐츠
   ▼
Produce
실제 문서·Skill·Task·카드뉴스 등 결과물 생성
   ▼
Archive
원문과 결과를 연결하고 미처리 표시 해제
```

### 소셜 플랫폼의 읽기 제한

Instagram carousel, Threads와 X는 로그인·동적 렌더링·접근 제한 때문에 에이전트가 링크만으로 항상
읽을 수 없다. 첫 설계는 성공을 가장하지 않고 다음 순서를 갖는다.

1. 원 URL과 공유 시점 메타데이터를 먼저 보존
2. 플랫폼 API 또는 허용된 브라우저 읽기
3. 실패하면 모바일 공유 시 이미지·텍스트·자막 원본을 함께 첨부
4. OCR은 즉시 최종 요약을 만들지 않고 **무손실 원문 큐 + 신뢰도**를 남김
5. 누락된 carousel 장수, 잘린 본문과 OCR 불확실성을 사람에게 보여줌

모바일 브라우저 제어, 클라우드 릴레이와 원격 로그인 세션은 보안·운영 비용이 큰 별도 설계다.
Codex Cloud나 Claude Code Cloud라는 특정 제품을 전제로 하지 않는다. 필요한 것은 “모바일 캡처를
원격 수집 워커에 안전하게 전달하고 결과를 다시 Inbox에 붙이는 릴레이”라는 역할이며, 인증·세션
보호·비용·실패 복구 ADR 후에만 구현한다.

### 기존 적체를 0으로 만드는 운영 캠페인

이 작업은 VHK Core 기능이 아니라 Yohan Inbox 운영 목표다.

1. 플랫폼별 저장 항목 수와 읽기 가능 여부를 inventory
2. 중복 URL·동일 콘텐츠를 fingerprint로 묶음
3. 원문 확보 실패 항목을 별도 보류 큐로 분리
4. 필요성·신선도·실행 가능성으로 1차 triage
5. 남길 항목은 지식·Skill 후보·Task·콘텐츠로 승격
6. 원문과 산출물의 연결을 확인한 뒤 처리 완료
7. “미처리 0, 보류 사유 전량 표시”를 종료 조건으로 사용

원문을 일괄 삭제하거나 읽음만 강제로 지워 0을 만드는 방식은 금지한다.

### 기존 자산과 외부 앱의 위치

| 자산·앱 | 재사용 방향 | 원본으로 맡기지 않을 것 |
|---|---|---|
| 기존 Telegram bot | 모바일 capture adapter, 실패 시 원문 보존 | 전체 지식·Task 상태 |
| 기존 Yohan Brain ingest | 장기 지식 승격 후보의 저장·검색 | 프로젝트의 현재 실행 상태 |
| Notion | 긴 문서, 외부 공유, 사람이 편집하는 화면 | AI 작업 문맥과 완료 판정의 유일한 원본 |
| NotebookLM·YouTube 자막 | 원문 이해와 리서치 보조 | 검증되지 않은 요약을 최종 지식으로 자동 승격 |
| 브라우저 워커 | 로그인된 동적 페이지의 허용된 읽기 | 인증 우회·무제한 세션 보관 |

ChatGPT·Claude 앱·CLI마다 GitHub와 외부 앱 접근 범위가 달라도, 최종 실행 에이전트는 같은 VHK 작업
문맥 계약을 읽게 한다. 특정 앱의 검색 결과를 전체 맥락으로 간주하지 않는다.

### Skill·Plugin 감사 원칙

정보에서 발견한 추천 도구를 바로 설치하거나 기존 것을 바로 지우지 않는다. 먼저 현재 커스텀
Skill·Plugin과 검증된 외부 구현을 같은 문제 기준으로 비교한다.

1. 해결하려는 문제와 실제 사용 빈도를 적는다.
2. 현재 커스텀 구현과 외부 후보의 기능·품질·유지보수·비용·지침 중복을 비교한다.
3. 결과를 **외부 채택 / 좋은 원리만 흡수 / 기존 유지 / 통합 / 폐기 후보**로 기록한다.
4. 격리된 실제 작업에서 기준선보다 나은지 검증한다.
5. 전역 비활성화·제거는 백업과 사람 승인 뒤에만 수행한다.

Superpowers, Caveman, OMC와 새로 발견한 Skill도 같은 절차를 따른다. 자동 감사가 삭제까지
진행하거나, “인기 있음”만으로 범용 코어에 승격해서는 안 된다.

## 4. 향후 결정 지도

| 영역 | 보존할 의도 | 지금 확정하지 않는 이유 | 열기 위한 조건 | 필요한 결정 |
|---|---|---|---|---|
| Canonical Task | 부모·자식, 범위, 수용 기준과 상태를 표준화 | ADR-010 원본과 이중화 위험 | 읽기 전용 투영 도그푸딩 | 원본 위치·마이그레이션 ADR |
| Task Graph | 의존성·차단·실행 가능 작업 계산 | v0에는 scheduler가 없음 | 실제 다중 Task 사례와 순환/충돌 fixture | DAG·선택 규칙 RFC |
| Task 쓰기 | start/result/state 전이를 의미 단위로 기록 | 원본 충돌·멱등성·롤백 미결정 | read-only 정확성 입증 | 이벤트·revision·reconciliation ADR |
| Task별 증거 | 완료 조건을 Receipt·Verify 결과와 연결 | 현재 증거는 저장소/커밋 단위 | 결정론적 Task↔change 연결 방법 | 기존 원장 재사용 ADR |
| Run 기록 | 에이전트 실행·재시도·비용·결과 추적 | autonomy/action log와 중복 위험 | 기존 로그 inventory | 단일 Run 원본 결정 |
| Approval | 요청·승인·철회·만료와 사람 인증 | 보안·권한 경계 | 인증된 사람 표면과 위협 모델 | 보안 ADR |
| 자율성 | guided/auto 같은 사람 개입 수준 | 동시성·작업 의도와 혼합되기 쉬움 | 작업 유형별 실패율 실측 | autonomy policy |
| 동시성 | 단독/병렬과 worktree 격리 | 파일 소유·병합 충돌 | 독립 Task 판정과 Orca 실측 | concurrency policy |
| 작업 의도 | build/recovery/release 같은 실행 목적 | 상태나 자율성 enum이 아님 | 반복 흐름이 안정될 때 | intent vocabulary |
| 전체 Context Compiler | 관련 결정·실패·파일·검증만 조립 | 검색 정확도와 토큰 기준 미측정 | WorkContext v0 평가 | source ranking·freshness RFC |
| Control Tower | current focus, next Task, blocker/approval UI | 데이터 소유권보다 UI가 앞설 위험 | Task/Run/Approval 읽기 계약 안정 | 화면·동기화 제품 spec |
| Yohan MCP | `getContext`, `startTask`, `recordResult` 같은 의미 도구 | 쓰기 계약·인증 미정 | 도메인 서비스와 권한 모델 | MCP surface RFC |
| Yohan Brain | 장기 지식·결정·패턴 검색 | 프로젝트 상태와 지식의 혼합 위험 | 지식 승격·출처 계약 | memory provider contract |
| Calendar | Task를 시간 블록에 배치 | Task 완료와 일정 종료를 혼동할 위험 | Task id와 일정 연결 규칙 | Calendar adapter spec |
| Evolution | 관찰→후보→실험→승격→롤백 | 규칙 비대화·잘못된 자동 승격 위험 | baseline과 비교 지표 | promotion/rollback ADR |
| Plugin 정리 | Caveman·Superpowers 등의 중복 제거 | 전역 설정 변경·롤백 필요 | inventory, 백업, 기준선 측정 | 대상별 사람 승인 |
| OMC 평가 | 역할 분리·루프 원리 비교 | VHK/Orca와 오케스트레이터 중첩 위험 | 격리 실험과 비용 기준 | 실험 계획, 기본 설치 아님 |
| 테스트 정책 | 핵심 로직은 테스트 우선, 단순 UI·탐색은 위험 기반 검증 | 현재 compact/auto 지침과 Proposed 철학 사이 행동 변경 | ADR-012 승인과 실제 작업 표본 | 별도 정책 감사·회귀 테스트 |

## 5. Control Tower와 MCP의 책임 경계

Control Tower는 모든 데이터를 직접 소유하는 단일 DB가 아니라 **단일 관제 지점**이다.

Control Tower가 답해야 할 질문:

- 지금 가장 중요한 프로젝트는 무엇인가?
- 오늘의 다음 행동은 무엇인가?
- 무엇이 막혔고 내 승인이 필요한가?
- 어떤 AI Run이 진행 중이며 결과 근거는 무엇인가?

Yohan MCP가 제공할 방향:

- 프로젝트와 현재 작업 문맥 읽기
- Task·Run·Approval의 의미 기반 동작 요청
- 검증 결과와 blocker 기록
- Brain 검색과 Calendar 배치 요청

MCP에 `readFile`, `updateRow` 같은 저수준 도구만 노출하면 에이전트마다 업무 규칙을 다시 구현하게 된다.
다만 의미 기반 **쓰기**는 Task 원본·인증·revision 계약 전에는 열지 않는다.

아래는 방향이지 아직 전체 승인된 계약이 아니다.

| 정보 | 예상 원본 | 이유 |
|---|---|---|
| 코드·테스트·프로젝트 문서 | Git/GitHub | 이식성·검토·버전 |
| VHK 프로젝트 작업 | 프로젝트가 선택한 Task 원본 | 범용 계약은 후속 ADR |
| 통합 Inbox·개인 우선순위 | 개인 통합 레이어 | 프로젝트 밖의 개인 운영 상태 |
| 장기 지식·관계·패턴 | Yohan Brain | 프로젝트를 넘는 기억 |
| 약속·미팅·시간 블록 | Google Calendar 등 기존 캘린더 | 시간 엔진을 재구현하지 않음 |
| AI Run·Approval | Control Tower 도메인 또는 명시된 Run Store | 여러 프로젝트 통합 조회 |
| 검증 결과 | 기존 VHK verify/receipt/ledger | 중복 증거 체계 금지 |

Task는 “무엇을 해야 하는가”, Calendar는 “언제 할 것인가”다. 시간이 끝났다고 Task를 자동 완료하지 않는다.

## 7. 재귀 개선의 안전한 형태

```text
Observe → Evaluate → Extract → Propose
   → 격리 실험 → 비교 검증 → 사람 승인 → Promote
                                      │
                               악화 시 Rollback
```

- 내부 사고 과정을 저장하지 않는다.
- 결정, 근거, 시도, 실패 원인, 검증 결과와 남은 위험만 남긴다.
- 한 번의 사례는 자동 Rule이 아니다.
- 범용 승격은 여러 프로젝트 근거와 사람 승인이 필요하다.
- 변경 전 기준선과 되돌릴 버전을 남긴다.

## 8. 권장 도입 순서

1. **1단계 문서 PR:** 원본 경계, Proposed ADR/RFC, 미래 지도와 대화 템플릿
2. **ADR 승인 + 2.13 안정화 뒤 PR B:** ProjectedTask·WorkContext 읽기 전용 출력
3. **도그푸딩:** Claude Code와 Codex에서 같은 입력·선택·경고 확인
4. **별도 ADR:** Task 원본·쓰기·증거 연결
5. **개인 통합 읽기:** Control Tower와 Yohan MCP에서 조회만
6. **승인된 쓰기:** Task·Run·Approval 한 영역씩
7. **Yohan Inbox 적체 정리:** 수집 품질과 미처리 0 운영 검증
8. **진화·플러그인 정리:** 기준선 비교 뒤 하나씩 실험

각 단계는 이전 단계의 실제 오류와 사용성을 확인한 뒤 연다. 한 번에 전체 생태계를 재구축하지 않는다.

## 9. 이 지도에서 의도적으로 정의하지 않는 것

- 데이터베이스 제품과 클라우드 공급자
- 모바일 앱 프레임워크
- 원격 브라우저 로그인 우회 방법
- Task·Approval·Run의 최종 JSON 스키마
- 자동 머지·무인 배포
- 외부 플러그인 제거 명령

이 항목들은 구현 직전의 최신 공식 문서, 현재 자산과 보안 경계를 조사한 뒤 결정한다.
