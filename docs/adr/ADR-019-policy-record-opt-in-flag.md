# ADR-019: 권한 정책의 기본 off 를 기록·집행 두 플래그로 나눈다

## 맥락 (Context)

작업 단위 124(권한 단계 + 위험도별 승인)는 "활성화 플래그가 없으면 부작용 0"을 완료 조건으로 둔다.
설계 초안(RFC 0066 §11 Q5)은 그 원칙을 끝까지 밀어 **off 상태에서는 원장에도 쓰지 않기로** 했다.
원장 기록도 파일 변경이기 때문이다.

그 결정에는 알려진 순환이 딸려 있었다. 안 켜면 판정 이력이 없고, 이력이 없으면 "켜도 되나"를
판단할 근거가 없다. RFC 는 이 순환을 정직하게 적어두되 감수하기로 했고, 근거는
**"켜기 판단은 원장이 아니라 `vhk stats` 의 3중 판정 지표(이미 4주간 쌓이는 중)로 하면 된다"** 였다.

구현 착수 전 실측에서 두 가지가 드러났다.

**첫째, 그 근거가 사실이 아니었다.** `.vhk/events/` 에 `autonomy-run.jsonl` 도
`receipt-log.jsonl` 도 없다. `vhk stats` 는 "표본 없음", 관찰 게이트는 "관측 완료 0/10개"를
출력한다. 대안 데이터가 쌓이는 중이 아니라 존재하지 않았다.

**둘째, 이것은 순환이 아니라 데드락이다.** 코드 경로로 확인했다.

```text
enforce 를 켜는 시점에 원장 0줄
  → RFC 0066 §4.4 케이스 0 → 무조건 L1
    → L1 은 커밋 금지 → 런 종료 시 작업 트리 dirty
      → isVerifiedComplete 의 `!r.dirty` 실패 → verified=false
        → rollingSelfReportedOnly > 0 → 케이스 4 SELF_REPORT_GAP → hold
          → 영원히 L1
```

근거는 `src/commands/stats.ts` 의 `return !r.dirty && r.stale !== true` 다. `L1` 은 정의상
커밋을 못 하므로 구조적으로 `verified` 가 될 수 없고 승급 조건을 영원히 만들지 못한다.
현행 자율 런은 이미 `L3` 수준이므로(RFC 0063 — 커밋 직후 push + PR, 머지 0) 켜는 순간
두 칸 축소된 채 굳는다. 즉 **기능을 켜면 기능이 죽는다.**

## 결정 (Decision)

활성화를 **하나의 플래그가 아니라 두 단계**로 나눈다. `.vhk/policy.json` 에서 읽는다.

| 플래그 | 켜면 | 부작용 |
|---|---|---|
| `record` | 판정 이력을 `policy-decision.jsonl` 에 남긴다 | 원장 append 1줄. **집행 없음** |
| `enforce` | 기록 + 집행(작업 단위 126 이후) | 위 + 실제 명령 차단·중단 |

`enforce: true` 는 `record` 를 함의한다. 집행하면서 이력을 남기지 않는 경로는 만들지 않는다.

`record` 만 켠 상태에서는 판정이 실제 동작을 제약하지 않는다. 자율 런은 종전대로 커밋·push 를
하므로 작업 트리가 clean 이고, `verified` 가 정상적으로 성립해 이력이 쌓인다. 그 뒤 `enforce` 를
켜면 원장에 `level` 라인이 있어 케이스 0 을 밟지 않고, 케이스 2("표본 부족은 하강이 아니다")가
적용돼 현행 단계가 유지된다.

## 근거 (Rationale)

- **완료 조건은 유지된다.** "활성화 플래그 없이 실행 시 부작용 0"에서 말하는 상태는
  *아무 플래그도 없는 상태*다. 그 상태의 부작용 단언(RFC 0066 §7.5)은 그대로 둔다.
- **자동으로 켜지는 경로는 없다.** 집행 부작용이 생기려면 사람이 두 번 켜야 한다.
  `record` 는 사람이 편집기로 설정 파일에 직접 쓴다 — 켜는 CLI 명령을 만들지 않는 규율은
  `enforce` 와 동일하다.
- **대안을 버린 이유.**
  - (A) 원안 유지 — 데드락이 남는다. 기능을 켤 수 없으면 만들 이유가 없다.
  - (C) 판정 이력을 별도 비추적 경로에 보관 — 원장이 둘로 갈린다. 나중에 합치는 비용이
    지금 아끼는 비용보다 크고, 같은 사실에 두 원본이 생기는 것은 이 저장소가
    반복해서 피해온 실패 형태다(ADR-010 §2).

## 결과 (Consequences)

- RFC 0066 §7.1·§7.2·§7.4·§6, RFC 0067 §6.2·§6.3 이 두 플래그 기준으로 개정된다.
- `policy-config.ts` 는 `record`·`enforce`·`maxLevel` 을 독립 파싱한다. 셋 중 하나라도
  못 읽으면 자율 레인 fail-closed 다.
- `policy-log.ts` 의 append 는 `record || enforce` 조건에서만 호출된다.
- **관찰 게이트와 무관하다.** 이 ADR 은 기록 조건만 바꾼다. `enforce` 활성화와 2.15.0 발행
  판정은 여전히 게이트 통과 후다.
- 남은 전제: `record` 를 켜도 **자율 런이 실제로 돌아야** 이력이 쌓인다. 지금 표본이 0인
  근본 원인은 플래그가 아니라 실행이 없다는 것이다.
