# ADR-012: 에이전트 비종속 코어와 외부 방법론 흡수 경계

> 용어: ADR-011 대응표 참조.
>
> 상태: **Accepted — 2026-08-01 관리자 명시 승인.**
> 관련 설계: [RFC 0064](../rfc/0064-agent-agnostic-task-spine.md)

## 한 줄 결정

VHK는 에이전트와 개인 도구를 교체 가능한 외부 연결로 두고, 프로젝트 실행에 남아야 할 최소 규칙과
검증만 범용 코어에 둔다. 첫 변화는 기존 Goal의 **읽기 전용 투영**으로 제한한다.

## 맥락 (Context)

VHK가 오래 남기려는 자산은 특정 모델의 프롬프트가 아니다. 프로젝트 의도, 작업 정의, 실행 상태,
결정, 검증 결과와 롤백 가능한 학습이다. Claude Code, Codex, Cursor 같은 실행 표면은 앞으로도
바뀔 수 있다.

동시에 OMC, Superpowers, Shrimp Task Manager, Caveman 같은 도구를 상시 중첩하면 계획, 훅, 상태와
완료 판정의 주인이 여러 명이 된다. 좋은 원리는 참고할 가치가 있지만, 명령 체계와 방법론 전체를
겹치면 VHK의 동작을 설명하기 어려워진다.

현재 VHK에는 이미 다음 계약이 있다.

- ADR-010이 정한 2.x 작업 정의 원본: 추적 roadmap·PRD
- 비추적 `goals/*.md`의 로컬 실행 상태
- 종료 코드 기반 verify와 저장소 수준 검증 리포트(receipt)
- 중단 신호와 사람 승인 경계

따라서 새 체계를 한 번에 만드는 대신, 무엇을 VHK에 남기고 무엇을 외부에 둘지 먼저 결정해야 한다.

## 결정 (Decision)

### 1. 상위 의도

VHK의 내부 북극성은 다음 문장으로 둔다.

> **에이전트는 바뀌어도, 시스템은 남고 검증을 통해 진화한다.**

이 문장은 공개 기능 완료 주장이 아니다. 외부 설명은 ADR-006과 ADR-011의 검증 중심 문구를 유지하고,
교차 에이전트 내성과 재귀 개선은 실측 근거가 생긴 범위에서만 주장한다.

### 2. 범용 코어와 개인 통합 레이어

공개·범용 부분을 **VHK Core**로 부른다. VHK Core는 다음 성질만 소유한다.

- 에이전트와 무관한 작업 입력·출력의 최소 계약
- 한 작업의 상태 전이와 완료 판정 규칙
- 검증과 사람 승인 경계
- 어댑터가 지켜야 할 최소 인터페이스

개인 지식 저장소, 통합 Inbox, 관제 화면, 캘린더, 특정 MCP와 자동화는 **개인 통합 레이어**가 맡는다.

```text
개인 통합 레이어 → VHK Core 의존 가능
VHK Core           → 개인 통합 레이어 의존 금지
```

VHK Core에는 특정 개인 서비스, 계정, 저장소 이름이나 로컬 경로를 하드코딩하지 않는다.

이 ADR은 모든 프로젝트의 작업 저장 위치를 Git으로 확정하지 않는다. 현재 VHK 저장소에 대해서는
Accepted 상태인 ADR-010의 roadmap·PRD 원본을 그대로 따른다. 범용 저장 계약은 실제 이식 요구가 생기면
별도 ADR로 결정한다.

### 3. VHK가 개입하는 시점

아이디어 발산, 링크 수집, 정보 정리와 초기 리서치인 DISCOVER는 VHK 실행 루프 밖에 둔다.
실제로 만들기로 결정한 뒤 DEFINE에서 문제, 범위, 성공 조건과 높은 영향의 회색 영역을 정리하고
VHK 실행으로 넘긴다.

```text
DISCOVER(외부) → 만들기로 결정 → DEFINE → EXECUTE → VERIFY
```

VHK는 정보 수집 앱이나 대화 도구를 대체하지 않는다. 사람에게 보이는 기본 흐름도 위 세 동사
DEFINE, EXECUTE, VERIFY를 우선하고 내부 기능만큼 명령을 늘리지 않는다.

### 4. 실행 루프 권한자는 하나

한 작업에서 상태 전이, 재시도와 완료 판정을 소유하는 실행 루프는 하나만 둔다. 다른 에이전트나
오케스트레이터를 보조로 사용할 수는 있지만 둘 이상의 루프가 동시에 “완료”를 결정하면 안 된다.

자율성 수준, 병렬 여부, 복구·릴리스 같은 작업 의도는 서로 다른 축이다. 이 ADR에서 하나의
`execution.mode` 열거형으로 합치지 않으며, 필요할 때 각각 별도 정책으로 설계한다.

### 5. 경계가 있는 자율성

에이전트는 정해진 범위 안에서 조사, 코드 변경, 로컬 검사와 실패 후 재시도를 할 수 있다.
다음 경계는 사람 승인을 유지한다.

- 제품 범위와 되돌리기 어려운 아키텍처 변경
- 인증·결제·보안·권한 정책
- 파괴적 삭제, 데이터 마이그레이션, 시크릿·권한 변경
- 외부 발송, 운영 배포, publish, main/master 머지
- 여러 프로젝트에 적용되는 공통 Rule·Skill·Workflow의 승격

완료는 에이전트의 문장이 아니라 수용 기준과 검증 결과로 판정한다.

### 6. 외부 방법론은 clean-room 방식으로 흡수

외부 도구는 상시 중첩 설치의 기본값이 아니라 설계 참고 원천으로 취급한다.

| 참고 원천 | 참고할 원리 | 기본 체계에 그대로 들이지 않을 것 |
|---|---|---|
| OMC | 역할 분리, 한 주 실행 루프, 구현-검증 반복 | 고정 에이전트 군, 모든 작업의 멀티에이전트화, 반복 루프 중첩 |
| Superpowers | 구현 전 성공 조건, 원인 중심 디버깅, 독립 검증 | 모든 작업의 장문 계획·엄격 TDD·자동 절차 주입 |
| Shrimp Task Manager | 지속 상태, 의존성, 차단 이유 | 별도 Task 원본, 내부 사고 과정 저장, 명령 중심 UX |
| Caveman | 필요할 때의 출력 압축 | 전역 자동 활성화와 판단 근거까지 지우는 강제 축약 |

기본은 외부 코드·프롬프트·템플릿을 복사하지 않고, 관찰한 요구와 불변식을 VHK 용어로 독립 구현하는
clean-room 방식이다. 코드를 직접 가져와야 할 때만 대상 파일, 라이선스, 저작권 고지와 보안 검토를
별도로 기록한다.

이 ADR은 Caveman, Superpowers, OMC 또는 다른 전역 플러그인의 삭제·설치 승인이 아니다.
그 작업은 현재 설정 목록, 백업, 영향과 롤백 절차를 확인한 뒤 대상별 사람 승인을 받아야 한다.

### 7. 기존 Goal 옆에 읽기 전용으로 시작

첫 변화는 기존 Goal을 없애거나 새 Task 원본을 만드는 일이 아니다.

1. ADR-010의 roadmap·PRD를 작업 정의와 수용 기준의 원본으로 유지한다.
2. `goals/*.md`가 있으면 로컬 실행 상태의 보조 입력으로만 읽는다.
3. 새 표현은 메모리 또는 표준 출력에서 만드는 읽기 전용 투영이어야 한다.
4. roadmap, PRD, Goal, `.vhk/context.md`, `docs/state/next-task.md`를 수정하지 않는다.
5. 기존 Goal 선택 순서와 공개 CLI·MCP 계약을 바꾸지 않는다.
6. 증거가 Task에 결정론적으로 연결되지 않으면 canonical done을 만들지 않는다.

구체적인 최소 읽기 계약과 검증 계획은 RFC 0064가 제안한다. ADR이 Accepted 돼도 코드 구현은 현재
2.13 작업 115~118 완료와 공통 게이트 통과 뒤 별도 PR로 시작한다.

### 8. 쓰기와 확장은 별도 결정

다음 항목은 이 ADR의 승인 범위가 아니다.

- Task 전용 영구 저장소와 상태 전이 쓰기
- 부모·자식·의존성 그래프와 새 next 스케줄러
- Task별 Evidence·Run 연결
- 승인 요청·승인 결정·멱등 쓰기 계약
- 외부 관제 화면, 원격 MCP, 클라우드 DB와 캘린더 쓰기
- 자동 병렬 실행, 자동 승격·롤백 엔진

이들 중 원본 소유권, 인증, 외부 쓰기 또는 되돌리기 비용이 큰 항목은 각각 별도 ADR이 필요하다.
구상은 [미래 설계 지도](../reference/agent-agnostic-future-map.md)에 보존하되 현재 계약처럼 구현하지 않는다.

## 대안 (Alternatives)

| 안 | 내용 | 판단 |
|---|---|---|
| A | 외부 방법론 플러그인을 모두 상시 중첩 | 상태·훅·완료 판정의 주인이 겹쳐 기각 |
| B | 기존 Goal을 즉시 새 Task 시스템으로 교체 | GA 계약과 ADR-010을 깨므로 기각 |
| C | 개인 관제·지식 시스템을 VHK Core에 직접 결합 | 공개 경계와 이식성을 깨므로 기각 |
| D | 아무 계약 없이 프롬프트 규칙만 추가 | 세션마다 해석이 달라져 기각 |
| **E** | **작은 VHK Core, 단방향 개인 통합, 읽기 전용 첫 단계** | 채택 |

## 결과 (Consequences)

### 장점

- 에이전트와 개인 도구가 바뀌어도 VHK Core의 책임이 유지된다.
- 기존 Goal과 검증 리포트를 재사용해 중복 코드와 이중 원본을 피한다.
- 읽기 전용으로 실제 효용을 먼저 확인한 뒤 쓰기 위험을 결정할 수 있다.
- 사용자가 기억해야 할 흐름과 용어를 작게 유지한다.

### 비용과 위험

- 첫 단계는 부모·자식, 의존성, 승인 쓰기와 관제 화면을 제공하지 않는다.
- Goal과 읽기 전용 투영이 잠시 함께 보이므로 “원본/파생” 표시가 정확해야 한다.
- 다른 에이전트에서 같은 결과가 나오는지 도그푸딩하기 전에는 이식성을 완료로 주장할 수 없다.

### 되돌리기

읽기 전용 투영과 JSON 출력을 비활성화하면 기존 roadmap·PRD + Goal 흐름으로 즉시 돌아간다.
첫 단계는 원본 파일을 쓰지 않으므로 데이터 역변환이 필요 없다.

## 이 ADR에서 확정하지 않는 것

- 범용 프로젝트의 Task 원본 위치와 파일 형식
- 읽기 전용 투영의 최종 타입명 외 영구 스키마
- 외부 관제·Brain·MCP·Inbox·Calendar의 제품 구조
- 플러그인 제거 시점과 전역 설정 변경
- 자동 머지, 무인 배포, 무승인 공통 규칙 승격

## 승인 기록과 남은 게이트

관리자는 2026-08-01 대화에서 **“ADR-012 Accepted. 115~118 선행 작업부터 진행.”**이라고 명시했다.
이 기록은 이 ADR의 상태 전이만 승인하며 main/master 머지나 배포 승인을 포함하지 않는다.

첫 코드 PR은 다음을 모두 만족해야 한다.

- 2.13 작업 115~118 완료와 공통 게이트 통과
- RFC 0064의 읽기 전용 범위만 구현
- 기존 원본 무쓰기와 Goal 선택 순서 회귀 테스트
- 별도 독립 검토
