# ADR-012: 에이전트 비종속 코어와 검증된 방법 흡수 정책

> 용어: ADR-011 대응표 참조.
>
> 상태: **Proposed — 관리자 승인 전에는 이 결정에 의존하는 코드를 구현하지 않는다.**
> 관련 설계: [RFC 0064](../rfc/0064-agent-agnostic-task-spine.md)

## 맥락 (Context)

VHK는 이미 특정 모델의 판단이 아니라 저장소 파일, 종료 코드, 테스트와 빌드 결과에 의존하는
에이전트 비종속 하네스를 지향한다. RFC 0057은 실행 계층이 대체로 에이전트와 무관하다는 점과,
트리거 계층·메모리 이식성에는 아직 공백이 있다는 점을 함께 기록했다.

그 뒤 다음 요구가 더 명확해졌다.

1. Claude Code, Codex, Cursor 등 실행 에이전트가 바뀌어도 프로젝트의 목표·현재 상태·다음 작업·검증 근거가 이어져야 한다.
2. OMC, Superpowers, Shrimp Task Manager, Caveman 같은 외부 방법론을 중첩 설치해 항상 실행하기보다, 실용적인 설계 원리만 VHK의 단일 체계로 흡수해야 한다.
3. 아이디어·정보 수집·리서치에는 강한 모델의 기본 능력을 그대로 쓰고, 실제로 만들기로 결정한 뒤부터 VHK가 프로젝트 실행을 맡아야 한다.
4. 프로젝트 관리와 작업 상태는 특정 앱의 내부 데이터에 갇히지 않고, 어떤 에이전트도 읽을 수 있는 공개 계약과 기계 증거로 남아야 한다.
5. 자가개선은 규칙을 자동으로 계속 추가하는 일이 아니라 제안, 격리 실험, 검증, 승인, 승격, 롤백이 가능한 폐쇄 루프여야 한다.

현재 VHK의 Goal 계약은 단일 작업을 고르고 검증하는 데 유용하지만 부모·자식 작업, 의존성,
차단 이유, 승인, 실행 모드, 증거 참조를 하나의 공통 계약으로 표현하지 못한다. 반대로 이를 한 번에
교체하면 GA 명령과 파일 형식의 안정성 약속을 깨뜨릴 위험이 있다.

따라서 이번 결정은 “새 프로젝트 관리 앱을 만든다”가 아니라, **기존 VHK 위에 이식 가능한
프로젝트 실행 척추를 어떻게 추가할지**를 정한다.

## 결정 (Decision)

### 1. 상위 의도와 공개 정체성을 분리한다

VHK의 내부 아키텍처 북극성은 다음 문장으로 둔다.

> **에이전트는 바뀌어도, 시스템은 남고 검증을 통해 진화한다.**

여기서 남아야 하는 시스템 자산은 의도·프로젝트 상태·작업 그래프·정책·결정·검증 증거·학습과
롤백 이력이다. 모델, IDE, CLI, MCP와 프롬프트 형식은 교체 가능한 실행 표면이다.

이 북극성은 ADR-006·ADR-011의 공개 정체성을 대체하지 않는다. 외부에는 계속
“AI 코딩 결과를 테스트·빌드 결과로 대조하는 1인 개발자용 검증 도구”라고 설명한다.
에이전트 비종속성과 자가진화에 대한 더 강한 주장은 실제 교차 에이전트·반복 개선 증거가 쌓인 뒤에만 공개한다.

### 2. 범용 Core와 개인 통합 레이어의 의존 방향을 고정한다

VHK Core는 다음 범용 계약만 소유한다.

- 정의 패킷과 작업 계약의 스키마
- 상태 전이, 의존성, 차단·승인 규칙
- 실행 모드와 단일 실행 루프 불변식
- 검증 계획, 증거 참조, 완료 판정 규칙
- 에이전트·도구 어댑터가 지켜야 할 최소 인터페이스
- 개선 후보의 실험·승격·롤백 계약

개인 지식 저장소, 통합 관제 화면, 캘린더, 특정 MCP와 자동화는 별도 **개인 통합 레이어**가 맡는다.

```text
개인 통합 레이어 → VHK Core 의존 가능
VHK Core           → 개인 통합 레이어 의존 금지
```

VHK Core에는 특정 개인 서비스나 저장소 이름을 하드코딩하지 않는다. Core는 provider·adapter 계약만
정의하고, 실제 연결은 외부 레이어가 선택한다.

### 3. 프로젝트 저장소가 작업 인스턴스의 원본이다

VHK는 Task 스키마와 상태 규칙을 정의하지만, 모든 프로젝트의 작업을 중앙 데이터베이스에 소유하지 않는다.

- 제품 작업 인스턴스와 완료 조건의 원본: 해당 프로젝트의 Git 저장소
- 현재 VHK 저장소의 구체적 원본: ADR-010이 확정한 추적 문서인 roadmap·PRD
- 기존 goals 카드는 원본 문서에서 파생되는 비추적 실행 카드이며 원본 후보가 아님
- VHK의 역할: 원본을 읽고 정규화된 Task Graph·실행 문맥·검증 결과를 만든다
- 외부 관제 화면·검색 인덱스의 역할: 읽기 최적화 복제본과 명령 표면
- 외부 복제본이 원본을 덮어쓸 때: VHK 상태 전이 계약과 기대 리비전을 반드시 통과

물리 파일 경로와 운영 데이터베이스 선택은 이 ADR에서 확정하지 않는다. **의미 소유권과 쓰기 경계만 먼저 고정한다.**
새 Task 파일을 opt-in 원본으로 허용하려면 ADR-010을 대체하거나 범위를 좁히는 별도 ADR,
원본 마이그레이션과 역변환 계획을 먼저 승인해야 한다.

### 4. VHK의 실행 경계는 실제로 만들기로 결정한 뒤다

아이디어 발산, 링크 수집, 정보 정리, 초기 리서치는 에이전트의 기본 대화·탐색 기능을 사용한다.
VHK는 그 과정을 매번 오케스트레이션하지 않는다.

```text
DISCOVER — 아이디어·수집·리서치, VHK 실행 루프 밖
DECIDE   — 실제로 만들기로 결정
DEFINE   — 문제·범위·성공 조건·회색 영역 확정
EXECUTE  — 실행 가능한 다음 작업 수행
VERIFY   — 기계 증거와 수용 기준으로 결과 판정
```

릴리스와 학습은 VERIFY 뒤의 확장 단계다. 사용자가 기억해야 할 기본 동사는 DEFINE, EXECUTE,
VERIFY 세 개로 제한하며, 내부 기능이 늘어나도 명령어를 같은 수만큼 늘리지 않는다.

### 5. 한 세션에는 하나의 실행 루프 권한자만 둔다

실행 정책은 native, guided, auto, parallel, recovery, release 모드를 표현할 수 있다. 이 이름은
당장 새 CLI 명령을 뜻하지 않고, 작업 계약이 실행 방식을 설명하는 표준 값이다.

- native: VHK 루프 밖의 조사·질문·작은 탐색
- guided: 사람 승인 지점을 포함한 단일 작업 실행
- auto: 정해진 범위와 완료 조건 안에서 반복 실행
- parallel: 독립 작업만 분리된 worktree에서 병렬 실행
- recovery: 실패 원인을 재현하고 수정·재검증
- release: 최종 품질 기준과 사람 승인 경계 확인

OMC·다른 오케스트레이터·VHK 루프를 동시에 권한자로 중첩하지 않는다. 여러 도구를 사용하더라도
현재 작업의 계획·재시도·완료 전이를 소유하는 루프는 하나여야 한다.

### 6. 자율성은 경계가 있는 자율성으로 제한한다

에이전트는 정해진 범위 안에서 다음 작업 선택, 코드 변경, 로컬 검사, 증거 기록, 실패 후 재시도를
할 수 있다. 아래 경계는 사람 승인을 유지한다.

- 제품 범위와 주요 아키텍처 변경
- 인증·결제·보안·권한 정책
- 파괴적 삭제, 데이터 마이그레이션, 시크릿·권한 변경
- 외부 발송, 운영 배포, publish, main/master 머지
- 공통 Rule·Skill·Workflow의 공식 승격

완료는 에이전트의 문장이 아니라 수용 기준과 검증 증거로만 전이한다.

### 7. 외부 방법론은 원리를 흡수하고 상시 중첩은 피한다

| 참고 원천 | 흡수할 원리 | 기본값에서 제외할 것 |
|---|---|---|
| OMC | 작업 크기별 실행 방식, 단일 주 실행 루프, 역할 분리, 구현-검증 반복 | 고정 에이전트 군, 모든 작업의 멀티에이전트화, 반복 루프 중첩 |
| Superpowers | 구현 전 성공 조건, 원인 중심 디버깅, 위험 기반 테스트, 독립 검증 | 모든 작업의 장문 계획·엄격 TDD·자동 절차 주입 |
| Shrimp Task Manager | 지속 작업 상태, 부모·자식, 의존성, 차단 이유, 다음 실행 가능 작업 | 별도 중앙 Task 원본, 내부 사고 과정 저장, 명령 중심 UX |
| Caveman | 필요할 때 선택하는 출력 압축 | 세션 전역 자동 활성화, 판단 근거까지 지우는 강제 축약 |

기본 정책은 **clean-room 재구현**이다. 외부 코드를 직접 가져올 때만 별도 라이선스·저작권·보안
검토를 수행하고 고지 의무를 지킨다. 기능 이름이나 훅을 그대로 복제하는 것이 아니라 VHK의 기존
계약과 용어로 다시 설계한다.

### 8. 기존 Goal 계약 옆에 점진적으로 추가한다

Task Spine은 기존 Goal, CLI 인자, MCP 도구, .vhk 파일을 즉시 대체하지 않는다.

1. 문서와 스키마를 먼저 승인한다.
2. 추적 roadmap·PRD 원본을 읽고, 존재할 때만 비추적 Goal 실행 카드의 상태를 보조 입력으로 사용하는 단방향 어댑터를 추가한다.
3. 새 투영이 기존 다음 작업 선택을 그대로 보존하거나 증거 부족을 별도 경고로만 표현하는지 도그푸딩한다. 기존 결과보다 더 허용적인 판정은 금지한다.
4. 새 쓰기 경로는 별도 승인 뒤 opt-in으로 연다.
5. 기존 계약의 폐기는 사용 증거와 별도 ADR 없이는 하지 않는다.

신규 필드는 optional로 시작하고, GA 안정성 약속을 지킨다.

### 9. 자가개선은 검증된 승격과 롤백으로만 성립한다

실패, 재작업, 사용자 개입, 검증 결과에서 개선 후보를 자동 추출할 수 있다. 그러나 후보가 곧 규칙은 아니다.

```text
관찰 → 평가 → 후보 추출 → 격리 실험 → 비교 검증 → 사람 승인 → 승격 → 관찰/롤백
```

프로젝트 로컬의 저위험 조정은 정책이 허용하는 범위에서 적용할 수 있지만, 여러 프로젝트에 영향을
주는 Rule·Skill·Workflow 승격은 사람 승인을 필수로 한다. 모든 승격은 버전·근거·되돌리기 대상을 남긴다.

## 대안 (Alternatives)

| 안 | 내용 | 기각 사유 |
|---|---|---|
| A | OMC·Superpowers·Shrimp·Caveman을 함께 설치해 기능을 합친다 | 중복 훅·계획·검토·상태 원본이 생겨 어떤 계층이 행동을 만들었는지 설명하기 어렵다 |
| B | 중앙 Task Manager가 모든 프로젝트 작업을 소유한다 | 외부 서비스 장애와 어댑터에 프로젝트 지속 상태가 종속되고, 저장소만 이동했을 때 이어지지 않는다 |
| C | 기존 Goal을 즉시 Task Graph로 교체한다 | GA 계약과 현재 2.x 로드맵을 깨뜨리고, 되돌리기 비용이 크다 |
| D | 문서 원칙만 두고 상태·증거 계약은 만들지 않는다 | 세션이 바뀔 때 같은 해석 문제가 반복되어 에이전트 비종속성이 선언에 머문다 |
| **E** | **범용 Core + 외부 통합 레이어, 저장소 원본, 점진적 Task Spine (제안)** | 구현 속도는 느리지만 책임과 롤백 경계가 가장 명확하다 |

## 결과 (Consequences)

### 긍정

- 에이전트·IDE·오케스트레이터를 바꿔도 프로젝트 상태와 증거가 남는다.
- 외부 도구의 좋은 원리를 한 계약으로 통합하면서 중복 훅과 명령 체계를 줄일 수 있다.
- 현재 2.x Goal·검증 흐름을 깨지 않고 실제 도그푸딩으로 전환 시점을 결정할 수 있다.
- 개인 통합과 공개 VHK Core의 결합 방향이 단방향이라 공개 경계를 유지할 수 있다.

### 비용과 위험

- 한동안 Goal과 TaskContract 두 표현이 공존한다. 어댑터 정합성 검사가 없으면 이중 원본처럼 보일 수 있다.
- 트리거 계층의 벤더 차이는 여전히 남는다. 지원을 주장하기 전 각 도구의 실제 자동화 표면을 조사해야 한다.
- 외부 관제 화면과 저장소 사이의 쓰기 충돌을 막으려면 기대 리비전·멱등성 계약이 필요하다.
- 개선 지표를 잘못 고르면 규칙이 비대해질 수 있다. 승격 전 비교 증거와 롤백을 강제해야 한다.

### 되돌리기

Task Spine은 추가형·opt-in으로만 구현한다.

- Wave 1~2 읽기 전용 투영·Context Compiler: 기능을 비활성화하고 파생 cache를 재생성하면 기존 roadmap·PRD 원본 + Goal 실행 경로로 즉시 돌아간다.
- Wave 3 이후 제한 쓰기: append 이벤트는 삭제하지 않고 보존한 뒤, 반영 여부를 원본 revision과 대조해 reconciliation 기록을 남긴다. 미반영 쓰기는 pending 또는 rejected로 종결한다.
- 새 Task 파일을 원본으로 허용하는 단계: 별도 ADR에 마이그레이션·역변환·이중쓰기 금지·롤백 절차가 없으면 시작하지 않는다.

기존 Goal 파일·명령·검증 형식은 이 ADR로 변경하지 않는다.

## 이 ADR에서 확정하지 않는 것

- Task 인스턴스의 최종 물리 파일 경로와 직렬화 형식
- 클라우드 운영 DB, 모바일 동기화, 캘린더 쓰기
- 특정 에이전트별 SessionStart/Stop 대체 트리거
- 기존 외부 플러그인의 실제 삭제 시점과 전역 설정 정리 명령
- 자동 머지, 무인 배포, 공통 규칙의 무승인 승격

## 승인 게이트

관리자는 이 ADR의 실제 문서를 검토한 뒤 명시적으로 Accepted 여부를 결정한다. 승인 전 허용 범위는
RFC·조사·테스트 계획 작성까지다. TaskContract 코드, 새 MCP 쓰기 도구, 외부 관제 화면의 상태 쓰기,
전역 플러그인 제거는 착수하지 않는다.
