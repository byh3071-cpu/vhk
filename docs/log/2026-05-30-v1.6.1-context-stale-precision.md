# 2026-05-30 — v1.6.1: context-stale 드리프트 감지를 file-change 기반으로 정밀화

> ⏪ 백필 항목 (2026-05-31 작성). 당시 Dev Log 미적재분을 git 커밋·PR 근거로 복원.

## 요약

v1.6.0 의 checkContextDrift 는 HEAD sha 가 context.md 생성시점과 다르기만 하면 무조건 stale 판정 →
README 오타 1커밋에도 "context.md 낡음" 오경보가 떴다. v1.6.1 은 generatedSha→HEAD 사이에
context.md 가 실제 반영하는 소스(package.json, goals/, docs/state/learnings.md 내용 변경, 또는
추적트리 파일 추가/삭제/이름변경)가 바뀌었을 때만 stale 판정하도록 정밀화. 시그니처·extractContextSha·
CRLF 로직은 GA 안정성을 위해 불변 유지.

## 교훈

1. 드리프트/stale 판정은 '커밋 sha 변경' 프록시가 아니라 '대상 산출물이 실제 반영하는 소스의 변경'을 직접 검사해야 오경보를 막는다. HEAD 변경=stale 같은 느슨한 기준은 무관 커밋(README 오타)에도 경고를 띄워 신호를 죽인다.
2. stale 판정 전 0단계 감사로 '산출물↔소스 매핑'(context.md 섹션↔소스 표)을 확정하면 관련/무관 경로 경계가 명확. 하드코딩·gitignore 소스(VHK 명령어·.vhk/memory.json·HARD_STOP)는 드리프트 대상 제외.
3. 감도를 매직넘버(N커밋)로 튜닝하지 말고 `git diff --name-only` 출력 유무 같은 결정론적 신호로 판정 → 임계값 추정 불필요. 디렉토리 구조 영향은 `--diff-filter=ADR` 로 내용 변경과 분리.
4. passive 경고 기능을 정밀화할 때도 공개 시그니처·헬퍼·CRLF 정규화는 불변 유지 → 동작 정확성만 바꾸고 API 는 안 건드려 GA 안정성 보존.
