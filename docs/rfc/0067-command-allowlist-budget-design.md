# RFC 0067 — 명령 허용목록 + 예산·시간 이중 집행 설계

> **상태: Draft — 오너 결정(2026-08-13)으로 구현 조기 착수.**
> 단 **`enforce` 활성화는 관찰 게이트 통과 후** — 코드는 전부 기본 off로만 들어간다.
> **예외 하나:** RFC 0066 §7.3의 설정 보호 조치(`.gitignore`·공개 경계·`PATH_RULES` 등재와
> 해시 베이스라인)는 `enforce`와 무관하게 **항상 동작한다.** 이 RFC의 허용목록·한도는 그 설정
> 파일 위에 서 있으므로, 보호 조치가 꺼지면 여기 있는 모든 검사가 같이 꺼진다.
> 게이트 조건은 그대로다: 4주 AND 유효 실행 10회 + 사람 승인.
> 이 문서의 파일 경로·타입·명령 이름은 **제안**이며 첫 커밋 직전에 재확인한다.

> 이 RFC는 [작업 단위 125](../roadmap/2.x-roadmap.md)의 T1~T4에 대응한다.
> **[RFC 0066](0066-permission-levels-design.md)이 선행이다.** 기록 봉투·권한 단계·설정 파일·
> 활성화 플래그·CLI 컨테이너를 전부 0066에서 정의하고 여기서는 재사용한다.
> 로드맵 §4가 124 → 125를 직렬로 묶은 근거("같은 기록 스키마")가 그것이다.

> **개정 이력**
>
> - **2026-08-20** 0066 §11 Q5 확정(옵트인 기록)에 맞춰 활성화 플래그를 `record`·`enforce` 둘로
>   기술한다. 이 RFC 고유의 판정·집행 규칙은 무변경 — 집행은 여전히 `enforce` 하나에만 걸린다.
>
> - **2026-08-13 (1차 적대 검증)** 골격 재작성. 판정 단계에서 위험도 축 제거(§4.1),
>   예산 근거를 자기 보고 원장에서 기계 계측 대리 지표로 교체(§5.5), 실행 측 판정 입력 한정(§5.3),
>   작업 범위 분리 제안 신설(§7).
> - **2026-08-13 (2차 적대 검증)** 잔여 구멍 마감. 런 단위 카운터와 시계를 **프로세스 밖 상태
>   파일**로 옮겼다(§5.3-3) — 1차 설계의 프로세스 지역 카운터는 매 호출 리셋됐고, 프로세스 지역
>   단조시각은 프로세스 경계를 넘지 못했다. 집행을 전부 125b로 통일(§7), `task-kind.ts` 소유를
>   RFC 0066으로 명시(§8), 손상 처리 어휘를 "자율 레인 fail-closed · 사람 CLI 무영향"으로 통일.

## 0. 요약

"이 명령을 지금 실행해도 되는가"를 **LLM 없이 룰과 하드리밋으로만** 판정하는 결정론 검사를 정의한다.

```text
실행 요청 ─▶ ① 중단 신호 ─▶ ② 허용목록 ─▶ ③ 호출 수 ─▶ ④ 시간 ─▶ ⑤ 권한 단계
              (HARD_STOP)     (정확 일치)     (기계 계측)   (단조 시계)   (minLevel)
                   │               │              │            │             │
                   └── deny ───────┴──── deny ────┴─── deny ───┘             └─ require-human
                       (exit 1)                                                  (exit 2)

같은 판정을 두 곳에서 각각 돌린다:
  호출 측(요청을 만드는 쪽) ──┐
                              ├─ 한쪽을 무력화해도 다른 쪽이 막는다
  실행 측(자율 레인 전용 진입점) ┘   단, 두 지점의 입력 범위는 다르다 (§5.3)
```

핵심 결정 다섯 가지.

| # | 결정 |
|---|---|
| 1 | 허용목록은 **셸 문자열이 아니라 argv 토큰 배열의 정확 일치**다. 와일드카드·정규식 없음 |
| 2 | **위험도(`riskClass`)는 명령 단위 판정에 쓰지 않는다.** 그것은 런 종결 행위의 축이다 |
| 3 | 하드리밋은 **기계가 직접 세는 값**(단조 시계 경과·명령 호출 수)만 쓴다. 자기 보고 비용은 참고 지표다 |
| 4 | 이중 집행의 두 지점은 같은 판정 함수를 쓰되 **설정을 각자 다시 읽고**, 실행 측 입력은 프로세스 환경으로 한정한다 |
| 5 | 실행 측 배선은 **125b로 분리**해 작업 단위 126과 같이 간다(§7). 로드맵 개정은 사람이 결정한다 |

## 1. 목표와 비목표

### 목표

- 실행 가능한 명령의 허용목록 형식과 로더를 정의한다(125-T1).
- 실행 전 결정론 검사의 **평가 순서와 정지 규칙**을 정의한다(125-T2).
- 시간·호출 수 한도를 호출 측과 실행 측 양쪽에서 집행하는 구조를 정의한다(125-T3).
- 위반 기록을 RFC 0066 §3의 공유 봉투 위에 얹는다(125-T4).
- 활성화 플래그가 없으면 판정만 하고 부작용이 0임을 설계로 보장한다(125-T4).

### 비목표

- 실행 자체. `vhk auto` 레인은 작업 단위 126이다. 이 RFC는 그 앞에 놓일 문지기만 만든다.
- 실행 후 출력 검증. 작업 단위 127이다.
- 세션 단위 서킷브레이커(무진전·반복 호출). 작업 단위 129다.
- LLM에 의한 명령 판단. 실패 비용이 큰 자동화는 결정 경로에서 LLM을 뺀다.
- 임의 셸 명령 실행. 이 저장소는 `execSync` 신규 사용을 금지하고 `safeExecFile`만 쓴다.
- 사용자별·머신별 허용목록 동기화. 파일은 로컬 하나다.
- **공용 `safeExecFile`에 집행을 얹는 것.** 근거는 §5.3.

## 2. RFC 0066에서 상속하는 것

**여기서 다시 정의하지 않는다.** 아래는 전부 0066의 산출물이다.

| 항목 | 출처 | 이 RFC의 사용 |
|---|---|---|
| 기록 원장 `.vhk/events/policy-decision.jsonl` | 0066 §3.1 | 같은 파일에 append |
| 공통 봉투 `PolicyDecisionV1` | 0066 §3.2 | **봉투 필드 불변.** 변형별 필드만 추가(§6.1) |
| `verdict` 3값 · `reasonCode` 닫힌집합 | 0066 §3.2 | 코드만 추가 |
| 권한 단계 `L0~L3` | 0066 §4.1 | 판정 ⑤의 입력 |
| 설정 파일 `.vhk/policy.json` | 0066 §7.4 | 같은 파일에 섹션 추가 |
| 활성화 플래그 `record` · `enforce` | 0066 §7.1·§7.4 | 같은 플래그 둘. `record` 는 기록만, `enforce` 는 기록+집행 |
| 손상 처리 규칙 | 0066 §7.4 | **그대로 상속.** 이 문서에 다른 해석을 두지 않는다 |
| 설정 파일 보호 조치 | 0066 §7.3 | 그대로 상속 |
| CLI 컨테이너 `vhk policy` | 0066 §8.1 | 서브커맨드 하나 추가 |

**0066의 §7.3·§7.4가 구현되기 전에는 이 RFC의 허용목록이 의미가 없다.**
설정 파일이 보호되지 않으면 자율 런이 허용목록에 한 줄 추가하는 것으로 모든 검사를 통과한다.

### 2.1 상속하지 않는 것 — 위험도 축

0066 §5.2의 단계 × 위험도 매트릭스는 **커밋·push 같은 런 종결 행위**에 적용된다.
이 RFC의 명령 단위 판정에는 적용하지 않는다. 근거는 §4.1이다.

## 3. 명령 허용목록 (125-T1)

### 3.1 형식 — argv 토큰 정확 일치

셸 문자열을 받지 않는다. 패턴 매칭도 하지 않는다.

```jsonc
// .vhk/policy.json — RFC 0066 §7.4의 파일에 섹션 추가
{
  "schemaVersion": 1,
  "enforce": false,
  "maxLevel": "L2",

  "allow": [
    { "id": "typecheck", "bin": "pnpm", "args": ["typecheck"], "minLevel": "L1", "maxDurationSec": 300 },
    { "id": "lint",      "bin": "pnpm", "args": ["lint"],      "minLevel": "L1", "maxDurationSec": 300 },
    { "id": "test",      "bin": "pnpm", "args": ["test:run"],  "minLevel": "L1", "maxDurationSec": 900 }
  ],

  "limits": {
    "perRunSec": 3600,
    "perCommandSec": 900,
    "perRunCommandCount": 40
  }
}
```

| 필드 | 형식 | 규칙 |
|---|---|---|
| `allow[].id` | string | 원장·출력에서 명령을 가리키는 안정 식별자. 파일 안에서 고유 |
| `allow[].bin` | string | 실행 파일 이름. 경로 구분자(`/`·`\`)·`..`·drive prefix 금지. 비교는 §3.4의 정규화 후 |
| `allow[].args` | string[] | **정확 일치 배열.** 빈 배열 허용. 와일드카드·정규식·변수 치환 없음 |
| `allow[].minLevel` | `'L0'~'L3'` | **이 명령을 돌리는 데 필요한 최소 권한 단계.** 미지정 시 기본값 `L3`(가장 엄격) |
| `allow[].maxDurationSec` | number? | 이 명령 개별 상한. 없으면 `limits.perCommandSec` |
| `limits.perRunSec` | number | **필수, >0.** 런 하나의 wall-clock 상한(초) |
| `limits.perCommandSec` | number | **필수, >0.** 명령 하나의 기본 상한(초) |
| `limits.perRunCommandCount` | number | **필수, >0.** 런 하나가 띄울 수 있는 명령 총 횟수 |
| `limits.perRunUsd` | number? | **참고 지표.** 판정에 쓰지 않는다 — 근거는 §5.5 |

> **`minLevel`은 적대 검증 지적(중대 11)으로 추가했다.** 초안의 판정 ③은 `LEVEL_TOO_LOW`를
> 반환하는데 "이 명령이 요구하는 최소 단계"가 스키마 어디에도 없어 계산이 불가능했다.
> 기본값을 `L3`로 두는 이유는 fail-closed다 — 사람이 명시하지 않은 명령은 가장 높은 단계에서만 돈다.

### 3.2 왜 정확 일치인가

| 대안 | 왜 안 쓰나 |
|---|---|
| 셸 문자열(`"pnpm typecheck"`) | 인용·이스케이프·연쇄(`&&`·`;`·`\|`)를 파싱해야 한다. 파서가 곧 우회 표면이 된다. 이 저장소는 이미 `execSync` 신규 사용을 금지하고 있다 |
| 정규식 인자 매칭 | ReDoS 표면이 생기고, 사람이 쓴 패턴 하나가 의도보다 넓게 매칭되는 사고가 조용히 난다 |
| 접두사 일치(`pnpm *`) | `pnpm publish`가 통과한다. 발행은 사람만 하는 일이다 |
| **argv 토큰 정확 일치** | **채택.** 매칭 로직이 배열 비교 한 줄이라 우회할 파서가 없다. 새 명령을 허용하려면 사람이 파일에 한 줄 더 쓴다 |

정확 일치의 비용은 유연성이다. `pnpm test:run --coverage`를 쓰려면 별도 항목을 추가해야 한다.
그 비용을 받아들인다. 로드맵의 방향은 "기능 추가가 아니라 실행 조건을 사람 손에서 떼는 것"이고,
허용목록은 그 손이 마지막으로 남는 자리다.

### 3.3 로더 계약

RFC 0066 §7.4의 손상 처리 규칙을 그대로 상속하고, `allow`·`limits` 섹션의 세부만 여기서 정한다.

| 항목 | 계약 |
|---|---|
| 파일 부재 | 빈 허용목록 → **자율 레인 fail-closed(전부 거부) · 사람 CLI 무영향** |
| `allow` 파싱 실패 | `allow` 섹션만 무효 → 빈 허용목록 → 자율 레인 fail-closed. `record`·`enforce`·`maxLevel`은 독립 파싱(0066 §7.4) |
| `allow` 항목 하나 무효 | **`allow` 섹션 전체를 무효화**한다. 항목 단위로 버리지 않는다 |
| `allow[].id` 중복 | `allow` 섹션 전체 무효 |
| `limits` 누락 | **섹션 무효 → 자율 레인 fail-closed** |
| `limits` 세 필수 값 중 하나라도 없거나 `≤0` | **섹션 무효 → 자율 레인 fail-closed** |
| `minLevel` 값이 `L0~L3` 밖 | 그 항목 무효 → `allow` 섹션 전체 무효 |
| BOM | `readJsonFile` 경유로 BOM-safe |

어느 행이든 결과 어휘는 하나다 — **자율 레인 fail-closed · 사람 CLI 무영향**(0066 §7.4).

> **`limits` 필수화는 적대 검증 지적(치명 5)이다.** 초안은 세 값을 전부 optional로 뒀는데,
> `evaluateBudget`은 `!limitUsd`일 때 `allow`를 반환하고(`src/lib/cost-policy.ts`) 시간 비교도
> `undefined`와의 비교라 통과한다. **한도를 안 쓰면 한도가 없어지는 fail-open**이었다.
> 자율 레인의 한도는 "안 쓰면 없음"이 아니라 "안 쓰면 못 돎"이어야 한다.

`allow`를 항목 단위가 아니라 섹션 단위로 무효화하는 이유는, 부분 로드가 "내가 쓴 3개 중 2개만
살아 있는데 어느 것이 죽었는지 모르는" 상태를 만들기 때문이다. 이것은 작업 단위 117이 고친
실패 형태("아직 도입 안 함"과 "설정이 깨짐"이 같은 경고)와 같은 종류다.

### 3.4 허용목록의 한계 — 정직하게 적어둔다

> **적대 검증 지적(중대 14)으로 신설한 절이다.** 허용목록은 **무엇을 띄우는가**를 막지
> **무엇이 실행되는가**를 막지 못한다. 이 경계를 문서에 적어두지 않으면 나중에 이 검사를
> 실제보다 강한 것으로 오해하게 된다.

#### 간접 실행 — 이 설계가 막지 못하는 것

| 경로 | 왜 새는가 |
|---|---|
| npm script 본문 교체 | `pnpm typecheck`는 허용목록을 통과한다. 그런데 `package.json`의 `scripts.typecheck` 본문은 바꿀 수 있고, 그 변경은 `TaskKind` 규칙상 `deps`(= `auto`)로 분류된다 |
| 설정 파일 경유 | `tsconfig.json`·`vitest.config.ts` 변경은 `chore`(= `auto`)인데 실행되는 내용을 바꾼다 |
| 실행 파일 자체 교체 | `node_modules/.bin` 아래 shim은 이 검사의 대상이 아니다 |

**이 계열에서 막지 않는다.** 대신 다음을 한다.

- `package.json`의 `scripts` 블록 변경을 위험도 `human`으로 올릴지는 **§12 Q4**로 남긴다.
- 스크립트 본문 해시를 런 시작 시 기록하고 종료 시 대조하는 안도 같은 질문에 넣는다.
- 지금 문서에 적어둔다 — **허용목록은 "사람이 승인한 명령 이름"의 목록이지 "사람이 승인한 동작"의 목록이 아니다.**

#### Windows shim — 집행 지점은 `resolveCmd` 이전

`src/lib/exec.ts`의 `resolveCmd()`는 Windows에서 `pnpm`·`npm`·`npx`·`yarn`·`vhk` 등을
`cmd.exe /d /s /c pnpm.cmd <args>`로 **재작성한다.**

| 함의 | 조치 |
|---|---|
| `resolveCmd` 이후에 허용목록을 대면 모든 명령의 `bin`이 `cmd.exe`가 된다 | **집행 지점은 `resolveCmd` 호출 이전**이다. 요청된 원래 `bin`·`args`로 판정한다 |
| Windows 파일명은 대소문자를 구분하지 않는다 | `bin` 비교는 **소문자 정규화** 후 수행 |
| `.cmd`·`.exe` 확장자가 붙거나 안 붙는다 | `bin` 비교는 **확장자를 제거**한 basename끼리 수행 |
| 호출부가 절대경로를 넘길 수 있다 | `bin`은 **basename만** 취해 비교한다(§6.1의 기록 규칙과 동일) |

정규화 순서를 고정한다.

```text
normalizeBin(raw) = basename(raw) → 확장자 제거 → 소문자 → trim
```

이 정규화가 느슨해 보일 수 있으나, 반대 방향(정규화 없이 원문 비교)은 Windows에서
`PNPM.CMD`가 허용목록을 통과하지 못해 검사가 실질적으로 꺼지는 결과를 낳는다.
꺼진 검사가 느슨한 검사보다 나쁘다.

## 4. 실행 전 결정론 검사 (125-T2)

### 4.1 위험도 축을 여기서 뺀 이유 (치명 2)

> **적대 검증이 잡은 카테고리 오용이다. 초안 설계의 판정 ③은 실제로 돌면 즉시 자기 자신을 막는다.**

`TaskKind`는 **런 종결 시점**에 계산된다. `src/commands/agent.ts`의 `deriveRunTaskKind()`는
같은 `runId`의 `start` 라인이 남긴 SHA부터 현재 HEAD까지의 diff 경로에서 유형을 유도한다.

런이 막 시작한 시점에는 그 diff가 비어 있다. 따라서

```text
런 시작 → 변경 0건 → deriveTaskKind([]) → 'unknown' → riskClass = human
        → 판정 ③에서 require-human
        → pnpm typecheck · lint · test:run 전부 막힘
```

**검증 명령 세 개가 첫 실행부터 전부 막힌다.** 자율 레인이 아무것도 못 한다.

원인은 축을 잘못 붙인 것이다.

| 축 | 무엇을 재나 | 언제 유효한가 | 어디에 쓰나 |
|---|---|---|---|
| `riskClass` | **이 런이 이미 무엇을 바꿨나** | 변경이 쌓인 뒤 | 커밋·push 같은 **결과 제출** 게이트 (0066 §5.2) |
| `minLevel` | **이 명령이 무엇을 할 수 있나** | 항상 | 명령 실행 전 검사 (이 문서) |

**판정에서 `riskClass`를 제거한다.** 명령 단위의 권한 검사는 허용목록 항목의 `minLevel`이 한다.
위험도는 0066 §5.2가 정의한 자리, 즉 런이 커밋·push를 하려 할 때 그대로 남는다.

### 4.2 판정 순서

**단락 평가다. 첫 거부에서 즉시 멈추고 나머지를 계산하지 않는다.**

> **순서도 적대 검증(치명 9)으로 재배열했다.** 초안은 단계 검사를 하드리밋보다 앞에 두어,
> `require-human`이 먼저 반환되면 예산·시간이 **한 번도 계산되지 않은 채** 사람이 승인하는
> 경로가 열렸다. 사람이 "응"이라고 한 순간 한도 없는 실행이 된다.
> **하드리밋을 전부 통과한 뒤에만 사람 승인을 묻는다.**

| 순서 | 검사 | 거부 시 `verdict` | `reasonCode` 예 | 성격 |
|---|---|---|---|---|
| ① | 중단 신호 — `.vhk/HARD_STOP` 존재 | `deny` | `HARD_STOP_ACTIVE` | 하드리밋 |
| ② | 허용목록 — 정규화된 `bin` + `args` 정확 일치 | `deny` | `NOT_IN_ALLOWLIST` | 하드리밋 |
| ③ | 호출 수 — 이 런의 누적 명령 수 대 `perRunCommandCount` | `deny` | `CALL_BUDGET_EXCEEDED` | 하드리밋 |
| ④ | 시간 — 런 누적 경과 · 명령 개별 상한 | `deny` | `TIME_LIMIT_EXCEEDED` · `TIME_LIMIT_WOULD_EXCEED` | 하드리밋 |
| ⑤ | 권한 단계 — 현재 단계 대 `entry.minLevel` | `require-human` | `LEVEL_TOO_LOW` | 승인 가능 |
| — | 전부 통과 | `allow` | `PREFLIGHT_PASSED` | — |

①이 첫 자리인 이유는 `HARD_STOP`이 이 저장소의 최상위 트립와이어이기 때문이다.
해제는 사람이 `vhk resume --confirm`으로만 하고, 자동 호출은 금지돼 있다.
그 규율을 자율 레인이 우회하는 순간 트립와이어가 무의미해진다.

①~④는 **사람 승인으로도 풀리지 않는다.** ⑤만 사람이 풀 수 있다.

### 4.3 종료 코드 — `require-human`을 0으로 두지 않는다

> **적대 검증 지적(치명 9의 후반).** 초안은 `require-human`을 exit 0으로 뒀다.
> 그러면 `vhk policy check ... && 실제실행` 형태의 셸 체인이 **승인 없이 그대로 통과한다.**
> 사람 승인이 필요하다는 판정이 성공 신호로 읽히면 그 판정은 없는 것과 같다.

| `verdict` | exit code | 의미 |
|---|---|---|
| `allow` | 0 | 그대로 진행 가능 |
| `deny` | 1 | 하드리밋. 사람도 못 푼다 |
| `require-human` | **2** | 사람 승인이 있어야 진행 가능 |

`&&` 체인은 0이 아닌 모든 값에서 멈춘다. 1과 2를 나누는 것은 사람과 로그를 위한 구분이다.

### 4.4 의사코드

```text
입력: request { bin, args }
      ctx { hardStopActive, allowlist, limits, level,
            runCommandCount, runElapsedSec }
출력: { verdict, reasonCode, matchedId? }

# ① 중단 신호
if ctx.hardStopActive:
    return deny(HARD_STOP_ACTIVE)

# ② 허용목록 — 정규화된 bin + args 정확 일치 (§3.4)
wanted = normalizeBin(request.bin)
entry = ctx.allowlist.find(e => normalizeBin(e.bin) == wanted
                             AND e.args.length == request.args.length
                             AND e.args 전부 같은 자리에서 문자열 동일)   # args 는 대소문자 구분
if entry == null:
    return deny(NOT_IN_ALLOWLIST)

# ③ 호출 수 — 기계가 직접 센 값 (§5.5)
if ctx.runCommandCount >= ctx.limits.perRunCommandCount:
    return deny(CALL_BUDGET_EXCEEDED)

# ④ 시간 — 런 누적 먼저, 그 다음 명령 개별
if ctx.runElapsedSec >= ctx.limits.perRunSec:
    return deny(TIME_LIMIT_EXCEEDED)
commandCap = entry.maxDurationSec ?? ctx.limits.perCommandSec
if ctx.runElapsedSec + commandCap > ctx.limits.perRunSec:
    return deny(TIME_LIMIT_WOULD_EXCEED)      # 끝날 수 없는 명령은 시작하지 않는다

# ⑤ 권한 단계 — 하드리밋을 전부 통과한 뒤에만 사람을 부른다 (치명 9)
if ctx.level < entry.minLevel:
    return requireHuman(LEVEL_TOO_LOW)

return allow(PREFLIGHT_PASSED, entry.id)
```

④의 마지막 조건이 중요하다. **끝날 수 없는 명령은 시작하지 않는다.**
남은 시간이 30초인데 상한 900초짜리 명령을 띄우면, 어차피 중간에 죽일 것을 위해
토큰과 시계를 쓴다. 작업 단위 127이 다룰 "폐기된 실행 비용"을 애초에 만들지 않는 쪽이다.

### 4.5 결정론 요구

| 요구 | 내용 |
|---|---|
| 시계 주입 | `runElapsedSec`는 파라미터다. 함수 안에서 `Date.now()`를 부르지 않는다 |
| 난수 없음 | 어떤 경로에도 없다 |
| 네트워크 없음 | 어떤 경로에도 없다 |
| 파일 읽기 없음 | 설정·원장은 호출부가 읽어 `ctx`로 넘긴다 |
| 프로세스 스폰 없음 | 판정 함수는 아무것도 띄우지 않는다(§5.3의 재귀 방지와 직결) |
| LLM 없음 | **결정 경로에 모델 호출이 없다.** 판정은 전부 룰과 하드리밋이다 |
| 같은 입력 → 같은 출력 | 100회 호출 동일 출력 테스트로 고정(§9.7) |

LLM을 결정 경로에서 빼는 것은 이 저장소의 기존 원칙이고, Goal 125 카드가 명시적으로
"이 작업 단위가 그 원칙의 구현"이라고 적어 두었다.

## 5. 이중 집행 (125-T3)

### 5.1 두 지점

| 지점 | 어디 | 무엇을 막나 | 왜 필요한가 |
|---|---|---|---|
| **호출 측** | 실행 요청을 만드는 쪽(작업 단위 126의 레인) | 요청 자체를 만들지 않음 | 실행 측에만 두면 호출이 폭주한 뒤에야 막힌다 |
| **실행 측** | **자율 레인 전용 exec 진입점**(§5.3) | 프로세스 생성·계속을 막고 죽임 | 호출 측에만 두면 그것을 우회한 경로가 무제한이 된다 |

Goal 125 카드의 완료 조건이 그대로 검증 조건이다.

> 한도 초과가 호출 측과 실행 측 **양쪽에서** 각각 막힘 (한쪽만 무력화해도 다른 쪽이 막음)

**두 지점 모두 작업 단위 126의 실행 레인이 있어야 존재한다.** 호출 측은 "실행 요청을 만드는
쪽"인데, 요청을 만드는 코드가 126의 레인이다. 따라서 §7의 분리에서 **호출 측·실행 측 집행이
둘 다 125b**에 들어간다. 125a가 만드는 것은 두 지점이 공유할 **판정기와 원장**뿐이다.

### 5.2 독립성 규칙

두 지점은 같은 순수 판정 함수를 부르지만, **입력 `ctx`를 각자 독립적으로 만든다.**

| 항목 | 규칙 |
|---|---|
| 설정 읽기 | 각 지점이 `.vhk/policy.json`을 각자 읽는다 |
| 중단 신호 | 각 지점이 `.vhk/HARD_STOP` 존재를 각자 확인한다 |
| 판정 결과 전달 | **금지.** 호출 측의 `allow`를 실행 측이 신뢰하지 않는다 |
| 판정 **입력** 전달 | **런 식별자(`runId`) 하나만 허용**(§5.3-3). 시각·카운터는 넘기지 않는다 — 상태 파일에 있다 |

판정 **결과**를 넘기면 이중 집행이 아니라 이중 표기다. 넘기는 순간 호출 측 하나만 무력화해도
실행 측이 그 거짓말을 그대로 통과시킨다.

판정 **입력**은 사정이 다르다 — §5.3이 그 경계를 정한다.

### 5.3 실행 측 재설계 — 재귀와 공용 통로 문제 (치명 10)

> **적대 검증이 잡은 두 가지 모순이다.**
>
> 1. **재귀.** 초안은 실행 측도 `riskClass`를 스스로 구하게 했다. 그러려면 `git diff`를 띄워야
>    하고, `git`은 `safeExecFile`을 거친다. 즉 **집행 지점이 자기 자신을 다시 호출한다.**
>    `git`이 허용목록에 없으면 모든 명령이 막히고, 있으면 무한 재귀 창이 열린다.
> 2. **공용 통로.** `safeExecFile`은 `vhk` 전체가 쓰는 범용 함수다. 사람이 부른
>    `vhk verify`·`vhk ship`·`git-repo.ts`까지 전부 여기를 지난다. 여기에 자율 레인 집행을
>    얹으면 사람이 부른 명령까지 허용목록에 걸리고, 그것을 피하려면 "지금이 자율 런인가"를
>    알아야 하는데 그 신호는 호출 측이 넘겨야 한다 — §5.2가 금지한 바로 그 전달이다.

**세 가지로 푼다.**

#### (1) 자율 레인 전용 진입점을 따로 둔다

```text
공용:      safeExecFile / safeExecFileAsync / safeExecFileStream   ← 무변경
자율 레인:  runGuardedCommand(request, runContext)                  ← 신설
              └─ 판정 통과 후에만 내부적으로 safeExecFile 을 호출
```

`safeExecFile`의 시그니처·동작을 바꾸지 않는다. 사람이 부른 경로는 영향이 0이다.
자율 레인은 `runGuardedCommand`만 쓰고, `safeExecFile`을 직접 부르지 않는다.
이 규율은 정적 검사로 고정한다 — 자율 레인 모듈의 import 그래프에 `exec.ts`가 직접 나타나면 실패.

"별도 모듈을 만들지 않는다"는 ADR-009와 부딪히지 않는다. ADR-009가 금지한 것은
**게이트를 이중 구현한 autonomous 모듈**이고, 여기서 만드는 것은 기존 `exec.ts`를 감싸는
얇은 진입점 하나다. 검사 로직은 §4의 순수 함수 하나뿐이고 그것도 호출 측과 공유한다.

#### (2) 실행 측 판정 입력을 프로세스 환경으로 한정한다

실행 측이 스스로 구할 수 있는 것만 쓴다. **스폰이 필요한 입력은 쓰지 않는다.**

| 입력 | 실행 측이 어떻게 얻나 | 스폰 필요 |
|---|---|---|
| `hardStopActive` | 파일 존재 확인 | 없음 |
| `allowlist` · `limits` | `.vhk/policy.json` 읽기 | 없음 |
| `level` | `policy-decision.jsonl` 마지막 `level` 라인 읽기 | 없음 |
| `runElapsedSec` | **런 상태 파일의 시작 벽시계 UTC**와 현재 UTC의 차(§5.3-3) | 없음 |
| `runCommandCount` | **런 상태 파일의 누적 카운터**(§5.3-3) | 없음 |
| ~~`riskClass`~~ | ~~`git diff` 필요~~ | **입력에서 제거**(§4.1) |

`riskClass`가 판정에서 빠졌으므로(§4.1) 실행 측이 `git`을 띄울 이유가 사라진다.
**치명 2의 수정이 치명 10의 재귀도 같이 닫는다.**

#### (3) 런 상태는 프로세스 밖에 있어야 한다 — 상태 파일

> **적대 검증 2차 지적(치명 4·10 잔여).** 1차 수정은 `runCommandCount`를 "진입점이 프로세스
> 내부에서 센 값", `runElapsedSec`를 "런 시작 단조시각과의 차"로 정의했다. **둘 다 프로세스
> 경계를 못 넘는다.**
>
> - **카운터:** overnight 에이전트는 명령마다 `vhk`를 **새 프로세스로** 부른다. 프로세스 내부
>   카운터는 매번 0에서 시작한다 → `perRunCommandCount`가 사실상 무한이 된다.
> - **시계:** Node의 `hrtime`·`performance.now()`는 **프로세스 지역 원점**을 쓴다. 다른
>   프로세스가 준 단조시각과 자기 단조시각을 빼면 의미 없는 수가 나온다. 1차 설계의
>   "더 이른 쪽을 쓴다"는 비교 자체가 성립하지 않았다.

**런 단위 상태를 디스크에 영속한다.**

| 항목 | 내용 |
|---|---|
| 파일 | `.vhk/run-state.json` (비추적 — `.gitignore` 등재) |
| 키 | `runId` — 병행 런이 서로를 덮지 않게 런별 레코드 |
| 필드 | `startedAtUtc`(ISO) · `commandCount`(number) · `lastSeenUtc`(ISO) · `clockAnomaly`(boolean) |
| 생성 | 자율 런 `start` 시점 1회 |
| 갱신 | 진입점이 **읽고 → `+1` → 기록** |
| 정리 | 런 종결 시 해당 레코드 제거. 종결 없이 남은 레코드는 오래되면 만료 |

#### 카운터 (치명 4 잔여)

```text
진입점 매 호출:
  1. run-state.json 에서 runId 레코드를 읽는다
  2. 레코드가 없으면 → 자율 레인 fail-closed (런 시작을 안 거친 호출)
  3. ctx.runCommandCount = 레코드의 commandCount
  4. §4.4 판정을 돌린다
  5. allow 면 commandCount + 1 을 기록한 뒤 실제 실행
```

5번이 **실행 전**인 것이 중요하다. 실행 후에 세면 프로세스가 죽었을 때 카운트가 누락되고,
죽는 명령을 반복하는 루프가 카운터를 영원히 올리지 못한다.

**원자성 한계.** 이것은 read-modify-write이므로 append 한 줄의 원자성이 적용되지 않는다.
RFC 0066 §4.5의 CAS 관례를 그대로 쓴다 — 읽은 값을 base로 기억하고, 기록 직전에 다시 읽어
`commandCount`가 base와 같을 때만 쓴다. 다르면 재계산한다.
0066 §4.5와 같은 한계가 여기에도 있다(파일 잠금 없는 낙관적 방식). 막으려는 것은
**같은 런 안에서 순차로 도는 명령들의 누락**이지 극단적 동시 쓰기가 아니다.

#### 시계 — 프로세스 경계를 넘는 기준 (치명 10 잔여)

두 층을 **다른 시계**로 잰다. 섞지 않는다.

| 층 | 시계 | 이유 |
|---|---|---|
| 명령 하나(`maxDurationSec`) | **프로세스 지역 단조시계** | 한 프로세스 안에서 시작·종료가 모두 일어난다. 단조시계가 정확하고 벽시계 변동에 면역이다 |
| 런 누적(`perRunSec`) | **벽시계 UTC 차** = 현재 UTC − `startedAtUtc` | 프로세스 경계를 넘어야 하므로 시스템 공통 기준이 필요하다 |

벽시계는 역행할 수 있다(NTP 보정·시간대 변경·수동 조정). 그것을 이렇게 다룬다.

```text
elapsed = nowUtc - startedAtUtc

if elapsed < 0:
    elapsed = 0                          # 음수 클램프
    record CLOCK_ANOMALY
    set state.clockAnomaly = true

if nowUtc < state.lastSeenUtc:           # 시간이 뒤로 갔다
    record CLOCK_ANOMALY
    set state.clockAnomaly = true

state.lastSeenUtc = max(nowUtc, state.lastSeenUtc)   # 단조 증가 강제

if state.clockAnomaly:
    → 자율 레인 fail-closed (그 런의 시간 한도를 더 이상 신뢰하지 않는다)
```

`clockAnomaly`가 한 번 켜지면 그 런은 끝난다. 시계가 흔들린 런에서 시간 한도를 계속
믿는 것보다 멈추는 쪽이 안전하다. 이것은 드문 상황이고, 드문 상황에서 관대해지는 것이
정확히 하드리밋이 뚫리는 방식이다.

`lastSeenUtc`를 단조 증가로 강제하면 **벽시계를 뒤로 돌려 경과를 줄이는 우회**도 같이 막힌다 —
경과는 `lastSeenUtc` 기준으로도 재계산되어 절대 줄지 않는다.

#### 호출 측이 실행 측에 전달하는 값

**`runId` 하나뿐이다.** 시각도 카운터도 넘기지 않는다 — 둘 다 상태 파일에 있다.

`runId`는 판정을 완화하지 않는다. 위조하면 존재하지 않는 레코드를 가리켜
위 2번에서 fail-closed된다. 다른 런의 `runId`를 가져다 쓰면 그 런의 카운터를 소모한다 —
얻는 것이 없다.

### 5.4 시간 집행 — 구현 메모

시계 선택의 근거와 이상 시계 처리는 §5.3-3에 있다. 여기서는 구현 지점만 적는다.

| 층 | 시계 | 구현 |
|---|---|---|
| 명령 하나(`maxDurationSec`) | 프로세스 지역 단조 | **새 메커니즘 없음** — `SafeExecOptions.timeoutMs`에 `maxDurationSec × 1000`을 넘긴다. 기존 timeout 처리(`ETIMEDOUT` 라벨링)를 그대로 쓴다 |
| 런 하나(`perRunSec`) | 벽시계 UTC 차 + 단조 증가 강제 | 상태 파일의 `startedAtUtc`·`lastSeenUtc` 기준. 명령마다 §4.4 ④로 재확인 |

원장의 `ts`는 기존대로 UTC ISO다. 이것은 기록용이지 판정용이 아니다.
판정에 쓰는 UTC는 상태 파일의 `startedAtUtc`·`lastSeenUtc`이며, 둘 다 §5.3-3의 이상 시계
처리를 거친다.

### 5.5 예산 재설계 — 자기 보고 위에 하드리밋을 세우지 않는다 (치명 4)

> **적대 검증이 잡은 근본 결함이다.** 초안은 `evaluateBudget(sumUsd(cost.jsonl), limit)`를
> 하드리밋으로 썼다. 그 원장의 실체는 이렇다.

| 사실 | 근거 |
|---|---|
| `cost.jsonl`은 **수동 입력**이다 | `src/lib/cost-ledger.ts` 주석: "vhk는 Claude API를 직접 호출하지 않아 비용을 자동 추적할 수 없으므로, 사용량은 외부 입력(`vhk cost add` 또는 환경변수)으로 먹인다" |
| `CostEntry`에 `runId`가 **없다** | 어느 런이 얼마를 썼는지 조인 불가 |
| `sumUsd`는 **전기간 전체 합**이다 | 런 단위 상한을 만들 수 없다 |
| 에이전트가 `cost add`를 안 부르면 `usedUsd = 0`이다 | 안 부르는 것이 가장 쉬운 우회다 |

**자기 보고 원장은 하드리밋의 근거가 될 수 없다.** 이것은 110 전체의 전제
("자기 보고는 카운터 자격이 없다")와 정확히 같은 논리다. 110이 완주율에서 자기 보고를 뺐는데
125가 예산에서 그것을 다시 들이면 같은 구멍을 다른 자리에 뚫는 것이다.

#### 채택 — 기계 계측 대리 지표

비용의 대리 지표로 **집행 지점이 직접 세는 두 값**을 쓴다.

| 지표 | 어떻게 세나 | 왜 대리로 쓸 만한가 |
|---|---|---|
| `runElapsedSec` | 단조 시계 차 | 벽시계 경과는 토큰 소모와 단조 증가 관계다. 오래 돌면 많이 쓴다 |
| `runCommandCount` | 진입점이 프로세스 안에서 증가 | 명령 호출 수는 루프 폭주의 직접 신호다 |

둘 다 **에이전트가 신고할 수 없는 값**이다. 진입점이 자기가 센다.
정확한 달러 금액은 아니지만, **막으려는 것은 금액이 아니라 폭주**다.

#### 병기 — `cost.jsonl` 확장안 (채택 안 함, 대안으로 기록)

`CostEntry`에 optional `runId`를 추가하고 자율 레인이 매 호출 후 직접 append하는 안이 있다.

| 장점 | 단점 |
|---|---|
| 실제 달러 금액으로 상한을 걸 수 있다 | **여전히 자기 보고다.** 안 부르면 0이다 |
| 런별 비용이 `vhk stats`에 노출된다 | 원장 스키마 변경이 필요하다(하위호환 optional이지만 추가 표면) |
| 작업 단위 127(폐기 실행 비용)과 자연스럽게 이어진다 | 127이 아직 없어 소비자가 없다 |

**최종 선택은 §12 Q2 — 사람이 정한다.** 그때까지 `limits.perRunUsd`는 파싱은 하되
**판정에 쓰지 않고 출력에만 표시**한다. 참고 지표라는 것을 출력 문구에 명시한다.

## 6. 위반 기록 + 중단 (125-T4)

### 6.1 기록 라인

RFC 0066 §3.2 봉투에 판별자 두 개를 추가한다. **봉투 필드는 하나도 바꾸지 않는다.**

`kind: 'allowlist'`

| 필드 | 형식 | 규칙 |
|---|---|---|
| `bin` | string | **`normalizeBin()`을 거친 값만**(§3.4) — basename · 확장자 제거 · 소문자 |
| `argCount` | number | **인자 개수만.** 인자 원문은 남기지 않는다 |
| `matchedId` | string \| null | 허용목록 항목 `id`. 미매칭이면 `null` |

> **`bin` 정규화는 적대 검증 지적(경미)이다.** 호출부가 절대경로를 넘기면 원장에
> 로컬 절대경로가 그대로 남아 이 저장소의 공개 경계 규칙을 **이 문서가 스스로 위반**한다.
> basename만 남기면 그 경로가 사라진다.

인자 원문을 남기지 않는 이유도 같다. 인자에는 파일 경로·토큰·URL이 들어올 수 있다.
`.vhk/events/`가 추적 금지 경로이긴 하지만, 원장 내용이 출력·요약으로 새는 경로가
그동안 여러 번 있었다. RFC 0065 §5.3이 진단에서 원문을 뺀 것과 같은 규율이다.

`kind: 'budget'`

| 필드 | 형식 | 규칙 |
|---|---|---|
| `dimension` | `'runSec' \| 'commandSec' \| 'callCount'` | 어느 한도인가. **`usd`는 없다**(§5.5) |
| `usedRatio` | number | 사용량 / 상한. 절대 초·횟수를 남기지 않는다 |
| `site` | `'call' \| 'exec'` | **어느 지점이 막았나.** 이중 집행의 검증 근거 |

`site`가 이중 집행 설계의 관측 지점이다. 실측에서 `exec`만 계속 나온다면
호출 측 집행이 실제로는 안 걸리고 있다는 뜻이다.

### 6.2 중단의 의미

| 상태 | "중단"이 뜻하는 것 |
|---|---|
| `enforce: false` (기본) | 집행 없음. 판정 결과를 stdout에 출력. `record: true` 면 판정 이력만 원장에 남는다(0066 §7.1) |
| `enforce: true` + 실행 레인 없음 (125a) | 원장에 기록. 막을 실행이 아직 없다 |
| `enforce: true` + 실행 레인 있음 (125b + 126) | 요청 거부 · 프로세스 미생성 또는 종료 |

### 6.3 기본 off

RFC 0066 §7.1의 4층 분리를 그대로 상속한다.

| 층 | 아무 플래그도 없을 때 | `record: true` 일 때 | `enforce: true` 일 때 |
|---|---|---|---|
| 판정 | 계산한다 (순수, 부작용 0, 스폰 0) | 같음 | 같음 |
| 표시 | `vhk policy check`가 결과를 출력한다 | 같음 | 같음 |
| 기록 | **쓰지 않는다** — 원장도, 런 상태 파일도 | 판정 이력만 원장에 남긴다 | 같음 |
| 집행 | 없다 | **없다** | 요청 거부·중단 (126 이후) |

런 상태 파일(§5.3-3)은 **자율 런이 시작될 때만** 생긴다. `enforce: false`에서는 자율 런이
돌지 않으므로 파일이 만들어지지 않는다. `vhk policy check`는 어떤 경우에도 이 파일을 쓰지 않고,
없으면 "런 밖 판정"으로 표시하며 `runCommandCount = 0`을 가정해 출력한다.

플래그도 0066 과 같은 것을 쓴다(`.vhk/policy.json` 의 `record`·`enforce` — ADR-019).
124용·125용을 **따로 두지 않는다** — 같은 안전 스위치가 기능마다 갈리면 하나만 켠 상태가 생긴다.
`record`/`enforce` 의 두 단계는 기능별 분기가 아니라 **기록과 집행이라는 다른 층**이며,
집행은 여전히 `enforce` 하나에만 걸린다.

## 7. 작업 범위 — 125a / 125b 분리 제안 (치명 7)

> **적대 검증이 잡은 문서 간 불일치다.** 초안은 실행 측 집행 배선을 작업 단위 126으로 미루면서
> 그것을 이 RFC 안에서만 선언했다. 그런데 로드맵과 PRD는 다르게 적혀 있다.

| 문서 | 125의 완료 조건 |
|---|---|
| 로드맵 §5 125-T2·T3 | "실행 전 결정론 검사" · "예산·시간 한도를 호출 측과 실행 측 **양쪽에서** 집행" |
| PRD §6-5 125 | "허용 목록에 없는 명령은 **실행되지 않는다**" · "양쪽에서 집행된다" |

RFC 하나가 조용히 범위를 줄이면, 125를 "완료"로 표시하는 순간 로드맵·PRD의 수용 기준이
충족되지 않은 채 닫힌다. 그것은 이 프로젝트가 110에서 고친 실패 형태와 같다.

**제안 — 로드맵을 사람이 개정한다.**

| 단위 | 범위 | 언제 |
|---|---|---|
| **125a — 판정기 + 기록** | 허용목록 로더 · 판정 순수 함수 · 런 상태 파일 · 원장 변형 · `vhk policy check` | 지금 (이 RFC 본문) |
| **125b — 집행** | 자율 레인 전용 진입점 · **호출 측 집행** · **실행 측 집행** · 프로세스 종료 | 작업 단위 126과 같은 릴리스 |

> **2차 검증에서 잡힌 모순을 여기서 닫는다.** 1차 수정은 125a에 "호출 측 집행"을 넣었는데,
> §5.1은 호출 측을 "126의 레인"으로 정의하고 §6.2는 "125a = 막을 실행이 아직 없다"고 적었다.
> 세 절이 서로 다른 말을 했다. **집행은 호출 측이든 실행 측이든 전부 125b다.**
> 125a에는 집행할 대상이 존재하지 않는다 — 그것이 §6.2 표의 두 번째 행이 뜻하는 바다.

**이 RFC는 로드맵을 고치지 않는다.** 개정은 사람 결정이다(§12 Q5).
개정 전까지 125의 완료 판정은 **125a·125b를 모두 채운 시점**이다.

125b를 126과 묶는 근거 셋.

1. 두 집행 지점 모두 **띄울 프로세스와 요청을 만드는 코드가 있어야** 실효 테스트가 된다.
   126이 그 소비자다.
2. 진입점 신설은 `exec.ts` 인접 변경이고, `TaskKind` 규칙상 그 경로는 `security`다 —
   사람 승인이 필요한 변경을 관찰 게이트 직후 첫 커밋에 섞지 않는다.
3. 125a는 순수 함수와 파일 I/O라 실행 없이 전수 테스트된다. 두 조각의 검증 방식이 애초에 다르다.

## 9. 테스트 전략

### 9.1 허용목록 (125-T1)

| 케이스 | 기대 |
|---|---|
| 정확 일치 | `allow` |
| 인자 1개 추가 / 누락 / 순서 바뀜 | `deny` · `NOT_IN_ALLOWLIST` |
| 인자 대소문자 다름 | `deny` — args는 구분한다 |
| `bin`이 `PNPM.CMD` | **`allow`** — `normalizeBin` 후 일치(§3.4) |
| `bin`이 절대경로 | basename 비교로 `allow`, 원장에는 basename만 |
| `bin`에 경로 구분자·`..` 포함(설정 파일 쪽) | 항목 무효 → `allow` 섹션 전체 무효 |
| `id` 중복 | `allow` 섹션 전체 무효 |
| `minLevel` 미지정 | `L3`로 취급 |
| `minLevel` 값이 `L9` | 항목 무효 → 섹션 무효 |
| 파일 부재 / 파싱 실패 | 빈 목록 → 전부 `deny` |
| `limits` 누락 / 값 `0` / 음수 | 섹션 무효 → 전부 `deny` (치명 5 회귀 가드) |
| BOM 있는 파일 | 정상 파싱 |

### 9.2 판정 순서 (125-T2)

| 케이스 | 기대 |
|---|---|
| `HARD_STOP` + 허용목록 통과 명령 | `deny` · `HARD_STOP_ACTIVE` |
| 미등재 명령 + 호출 수 초과 | `NOT_IN_ALLOWLIST` — ②가 ③보다 먼저 |
| **단계 부족 + 시간 초과 동시** | **`deny` · `TIME_LIMIT_EXCEEDED`** — 하드리밋이 먼저다(치명 9 회귀 가드) |
| 단계 부족만 | `require-human` · `LEVEL_TOO_LOW` · **exit 2** |
| 호출 수 정확히 상한 | `deny` — 경계 포함 |
| 남은 시간 < 명령 상한 | `deny` · `TIME_LIMIT_WOULD_EXCEED` |
| 전부 통과 | `allow` · `matchedId` 존재 · exit 0 |
| **런 시작 직후(diff 0건) 검증 명령 3종** | **전부 `allow`** — 치명 2 회귀 가드. 이 케이스가 이 절의 존재 이유다 |
| 판정 함수의 스폰 | 0건 |

### 9.3 이중 집행 (125-T3) — **125b 범위**

> 아래 케이스는 실행 측 진입점이 생긴 뒤에만 돌 수 있다. 125a에서는 판정 함수 단위 테스트로
> 대체하고, 이 표는 125b 완료 조건으로 이월한다.

| 케이스 | 기대 | 단위 |
|---|---|---|
| 호출 측만 살아 있음 | 요청이 만들어지지 않음 | 125b |
| 실행 측만 살아 있음 | 프로세스가 생성되지 않거나 종료됨 | 125b |
| 양쪽 다 살아 있음 | 호출 측이 먼저 막고 원장 `site: 'call'` | 125b |
| 호출 측 판정 **결과**를 실행 측에 주입 | 실행 측이 무시하고 스스로 재판정 | 125b |
| 존재하지 않는 `runId` 전달 | 상태 파일 레코드 없음 → 자율 레인 fail-closed(§5.3-3) | 125b |
| `runId` 외의 값(시각·카운터)을 넘기는 코드 | 정적 검사 실패 — 전달 표면은 `runId` 하나 | 125b |
| 실행 측 판정 중 스폰 발생 | 0건 — 재귀 회귀 가드(치명 10) | 125b |
| 자율 레인 모듈이 `exec.ts`를 직접 import | 정적 검사 실패 | 125b |
| 사람이 부른 `vhk verify`·`vhk ship` | 허용목록 영향 0 | 125b |

### 9.4 런 상태 — 카운터 (치명 4 잔여 회귀 가드)

| 케이스 | 기대 |
|---|---|
| **각 명령을 별개 프로세스로 실행** | 카운터가 리셋되지 않고 누적된다. **이 케이스가 이 절의 존재 이유다** |
| 상태 파일 레코드 없이 진입점 호출 | 자율 레인 fail-closed |
| `perRunCommandCount` 정확히 도달 | `deny` — 경계 포함 |
| 명령이 죽어도(비정상 종료) | 카운트는 이미 올라가 있음(실행 **전** 증가) |
| CAS 충돌(base 불일치) | 기록 안 함 · 재계산 |
| 병행 런 2개 | `runId`별 레코드가 서로를 덮지 않음 |
| 런 종결 | 해당 레코드 제거. 만료된 고아 레코드 정리 |

### 9.5 런 상태 — 시계 (치명 10 잔여 회귀 가드)

| 케이스 | 기대 |
|---|---|
| **다른 프로세스가 만든 `startedAtUtc`로 경과 계산** | 정상 동작. 프로세스 지역 단조시각을 프로세스 간에 빼는 코드가 없음(정적 검사) |
| 벽시계 역행(시간대 변경·NTP 모사) | 경과 음수 클램프 · `CLOCK_ANOMALY` 기록 · 자율 레인 fail-closed |
| `nowUtc < lastSeenUtc` | `CLOCK_ANOMALY` · fail-closed |
| 벽시계를 뒤로 돌려 경과 축소 시도 | `lastSeenUtc` 단조 증가 강제로 경과가 줄지 않음 |
| `clockAnomaly` 켜진 뒤 후속 명령 | 전부 fail-closed. 자동 해제 없음 |
| 명령 개별 상한 | 프로세스 지역 단조시계로 판정 · `timeoutMs` 경유 종료 · 좀비 없음 (125b) |
| 런 상한 정확히 도달 | `deny` — 경계 포함 |

### 9.6 시간·카운터 주입

판정 함수는 `ctx`만 본다. 상태 파일 읽기는 호출부 책임이므로,
판정 단위 테스트는 가짜 `ctx`로 전 경계를 돌린다(§9.7).

### 9.7 결정론

같은 `ctx`로 100회 호출해 동일 출력을 단언한다.

정적 확인의 대상은 **판정 모듈 3종**(`command-allowlist` · `execution-preflight` ·
`execution-limits`)이다. 이 셋에 `Date.now()`·난수·`fs`·네트워크·`child_process`가 없어야 한다
(기존 `scripts/check-*.mjs` 계열 패턴 재사용).

`run-state.ts`는 대상이 아니다 — 그 모듈은 정의상 `fs`를 쓴다. 경계는 이렇다.
**상태를 읽어 `ctx`를 만드는 것은 `run-state.ts`, 그 `ctx`로 판정하는 것은 순수 모듈 3종.**

### 9.8 기본 off 부작용 0

RFC 0066 §7.5의 8단계 절차를 그대로 쓴다.
`policy.json`이 `allow`·`limits`를 가지고 있어도 `enforce: false`면
**원장 라인이 0이고 `.vhk/run-state.json`도 생기지 않아야 한다.**

### 9.9 등록·별칭

`vhk policy check`와 `vhk 정책 검사` 둘 다 **인자를 붙여** 실측한다.
서브커맨드가 인자를 받는 경우가 이 저장소에서 인자 유실을 2회 일으켰다.
`CONTAINER_SUBCOMMAND_ALIASES`에 `check: 검사`를 등록하지 않으면
한글 경로가 자연어 라우터에 삼켜져 인자가 조용히 사라진다.

### 9.10 공통 검사

```text
pnpm typecheck && pnpm lint && pnpm test:run && pnpm build && pnpm boundary:check && pnpm security:audit
```

## 10. CLI 표면

RFC 0066 §8.1의 `vhk policy` 컨테이너에 **서브커맨드 하나만** 추가한다. 신규 top-level 명령 0.

| 항목 | 계약 |
|---|---|
| 실행 | **하지 않는다.** 판정 결과만 출력 |
| 파일 | 어떤 경로에서도 쓰지 않는다 |
| 스폰 | 0건 |
| 인자 구분 | `--` 이후를 대상 명령으로 읽는다. 그래야 `--json` 같은 플래그가 섞이지 않는다 |

| 종료 코드 | `allow` 0 · `deny` 1 · **`require-human` 2**(§4.3) |
| MCP | 노출하지 않는다 |
