## 2. 순서 원칙

2차 도그푸딩이 처방을 이미 써놨다.

> 다음 버전이 갈 방향은 기능 추가가 아니라 **기존 기능의 실행 조건을 사람 손에서 떼는 것**이다.

```
2.13 상태·첫 실행 신뢰 복구 ─▶ 2.14 작업 투영(134→135) ─▶ 측정(110→111) ─▶ 2.15 안전 정책(기본-off 공개)
                                                                                              │ 4주 AND 유효 실행 10회 · 사람 계속
                                                                                              ▼
                                                                    2.16 제한 실행 ─▶ 2.17 승인 경계
                                                                                               │
                                                                                               └─▶ 3채널 게시 (사람)
```

| 왜 이 순서인가 | 근거 |
|---|---|
| 2.13이 먼저 | 완료된 115~123이 미발행이고, Goal 상태·GitHub 이슈 상태가 실제 코드와 다르다. 여기에 첫 실행 무결성 결함 #544~#546도 남아 있다 |
| 선택기 가드를 먼저 둠 | 번호와 수동 상태만으로 다음 Goal을 고른 결과 110보다 124가 먼저 잡혔다. `depends_on`을 선택기가 직접 집행해야 같은 혼선이 반복되지 않는다 |
| 작업 투영이 계측보다 앞 | Goal 내부 Phase/Task를 같은 방식으로 읽어야 110·111의 작업 유형·상태 파악 시간도 일관된 실행 단위를 대상으로 잴 수 있다 |
| 2.14가 실행보다 앞 | ADR-009 ①: "실행 기능보다 권한 계측·검사 관리 먼저" |
| 관찰이 구현보다 앞 (2026-08-13·28 완화) | 기본-off 구현은 선행 가능하고, **2026-08-28 오너 결정으로 2.15 판정 기능의 패키지 공개도 허용**했다. `enforce` 활성화·2.16 집행 배선·관찰 대상 변경은 여전히 게이트 통과 후 (§관찰 게이트 개정 참조) |
| 2.15~2.17은 단계별 기본 off | 2.15 판정 기반은 관찰 중 선행 구현·기본-off 공개가 가능하다. 2.16 집행 배선과 2.17 머지 판정은 사람의 계속 결정 뒤에 구현한다 |

#### 136 — 저장소 경계 밖 Codex 훅 무해화 (P0)

> 저장소 로컬 훅이 세션 작업 디렉터리에서 실행될 때, 현재 Git 루트에 VHK 실행기가 없다는 이유만으로
> 도구 사용이나 세션 종료가 실패해서는 안 된다. 실행기가 있는 저장소의 차단·알림 계약은 그대로 유지한다.

| 136-T2 | Windows 훅은 Git 조회 실패·빈 루트·해당 파일의 `Leaf` 확인 실패에서 출력 없이 성공 종료 | `.codex/hooks.json` |

#### 137 — receipt 작업 기준선·검증 신선도 분리 (P0, #605)

> 작업 시작 SHA는 변경 범위와 의도 계약을 보는 기준선이다. 검증 증거가 낡았는지는 그 기준선이 아니라
> 실제 verify 리포트의 커밋 SHA와 현재 HEAD를 비교해야 한다. 두 역할을 섞어 정상 커밋을 BLOCK하지 않는다.

| 티켓 | 내용 | 대상 |
|---|---|---|
| 137-T1 | stale 판정을 작업 시작 SHA가 아니라 verify 리포트 커밋 SHA·dirty와 현재 HEAD·dirty의 대조로 계산 | `src/commands/receipt.ts` · `src/commands/verify.ts` |
| 137-T2 | 작업 시작 SHA와 `--since`는 intent의 커밋된 변경 범위 기준으로 계속 사용해 forbidden/scope 우회를 막음 | `src/commands/receipt.ts` |
| 137-T3 | 시작 A → 구현·커밋 B → B 검증이면 stale=false, 검증 B 뒤 HEAD C면 stale=true인 회귀 테스트 | `tests/receipt.test.ts` |
| 137-T4 | 기존 JSON 필드와 CLI 인자는 보존하되 도움말·사유·영수증 표가 작업 기준선과 검증 SHA를 구분하고, 생성 gate 스킬은 Goal 스키마 오류와 정상 전체-DONE closeout을 구분 | `src/lib/receipt.ts` · `src/i18n/ko.ts` · `src/lib/cursor-skill-templates.ts` · 문서 |
| 137-T5 | 실제 깨끗한 저장소에서 `vhk receipt`가 BLOCK하지 않고 같은 HEAD의 receipt-log를 남기는 도그푸딩 | 실측 |

- 자동 승인하지 않는다. 사람이 신뢰도와 병목을 보고 계속 또는 중단을 결정한다.

### 상위축 연결 (Accepted ADR-012·ADR-017 / RFC 0065)

RFC 0065의 첫 단계는 기존 Goal을 바꾸지 않고 본문의 Phase/Task를 읽는 투영뿐이다. 작업 단위
134·135로 2.14.0 앞에 편성하며, 아래 후속 자산은 미래 지도이고 현재 RFC의 구현 범위가 아니다.

| 현재 2.x 축 | 후속 작업 실행 계약에서 재사용할 수 있는 자산 |
|---|---|
| 2.13 상태·첫 실행 신뢰 | 스키마·Context Compiler가 틀린 상태를 자신 있게 말하지 않는 선행 조건 |
| 2.14 계측 | Run·재작업·개선 후보 baseline |
| 2.15 안전 정책 | 작업 위험도별 승인 규칙 |
| 2.16 제한 실행 | 한 실행 루프 권한자와 PR 상한 |
| 2.17 승인 경계 | bounded autonomy의 사람 판정 경계 |

구현 순서는 ADR-017·RFC 0065 계약 → Goal Phase/Task 파서(134) → 안전한 context JSON(135)
→ 완주 판정(110) → 병목 계측(111)이다. 새 쓰기 경로, 외부 관제 표면과 Task 간 명시적 의존성은
별도 결정 뒤에만 편성한다.

### npm dist-tag 정책 (2026-08-12 결정)

**`latest` 하나만 운용한다. `stable`은 폐지한다.**

| 항목 | 내용 |
|---|---|
| 무엇이 있었나 | 2.12.0까지 `latest`·`stable`이 같은 값이었다. 2.13.0 발행 때 `latest`만 이동해 `stable`이 2.12.0에 남았다 |
| 판정 | 의도된 "한 버전 뒤" 정책이 아니라 **이동 누락**이다. 정책이었다면 2.12.0 시점에 `stable`은 2.11.0이어야 했다 |
| 왜 이동이 아니라 폐지인가 | 외부 사용자 0이라 `@stable` 실사용자가 없다. 유지하면 발행마다 사람이 2단계 인증으로 태그 2개를 관리해야 하고, 그 관리가 이미 한 번 실패했다 |
| 되돌리기 | `npm dist-tag add` 한 줄. 외부 사용자가 생겨 안정 채널이 필요해지면 그때 다시 만든다 |
| 실행 | `npm dist-tag rm @byh3071/vhk stable` — **실 터미널에서 사람**. 보안키 2단계 인증이 비대화형 셸에서 `EOTP`로 실패한다(113-T1과 같은 제약) |
