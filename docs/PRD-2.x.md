# PRD — VHK 2.x 계열

> 용어: ADR-011 대응표 참조.
> 이 문서는 [docs/PRD.md](PRD.md)(제품 전체 정의)를 **대체하지 않는다.** 2.x 계열 한 사이클(2.13.0 ~ 2.17.0)의 요구사항만 담는다.
> 작업 단위·티켓·순서는 [docs/roadmap/2.x-roadmap.md](roadmap/2.x-roadmap.md)가 원본이다.

## 1. 한 줄 정의

**AI 코딩 결과를 테스트·빌드 결과로 대조하는 1인 개발자용 검증 도구** (ADR-011).

2.x 계열이 답하려는 질문은 하나다.

> 프로젝트 규칙을 문서에 써두면 실제로 지켜지는가? 안 지켜진다면, 무엇이 그걸 막는가?

### 버전 정책

| 항목 | 내용 |
|---|---|
| 계열 | 2.13.0 → 2.17.0 (마이너 5회 + 릴리스 없는 관찰 게이트) |
| 3.0.0 | **소각.** 2026-07-27 오발행 후 2.12.0으로 되돌림(`latest` 태그만 이동). 레지스트리에서 **unpublish**로 제거하되, 번호 재사용은 npm 정책상 영구 불가 |
| 다음 major | **4.0.0** |
| 호환성 | 명령어 이름·CLI 인자·`.vhk` 포맷·MCP 도구 시그니처의 breaking change 금지. 신규 필드는 전부 optional |
| 릴리스 리듬 | 미발행 10커밋 또는 2주 경과 시 배포 |

## 2. 문제 (Problem)

세 갈래 근거가 같은 곳을 가리킨다.

### 2-A. 2차 도그푸딩 25시간 실측 (2026-07-25 ~ 26)

실제 배포 예정 프로젝트에서 AI 에이전트 2대가 병렬 작업하는 환경을 25시간 연속 관측했다. 커밋 13건 전수 검사, `.vhk/` 파일 15개 수정시각 전수, 서브커맨드 60개 대조, 훅 발동 이력 실측.

**결론: 막는 기능은 살아남았고, 권고만 하는 기능은 전부 죽었다.** 경계는 "기능이 좋은가"가 아니라 **"사람이 다시 부르지 않아도 돌아가는가"** 하나로 갈렸다.

| 살아남은 것 | 이유 |
|---|---|
| `commit-msg` 기록 검사 훅 | 커밋이라는 행위 자체가 실행 조건이라 사람이 부를 필요가 없다. 소스 커밋 6건 중 5건에 세션 기록이 붙었고, 우회 토큰 남용 흔적 0 |
| `vhk sync` 전파 | RULES.md 수정 52초 뒤 파생본 8종이 갱신 |

| 죽은 것 | 방치 시간 |
|---|---|
| `vhk verify` 증거 | 19시간 |
| `vhk check` 규칙 점검 | 22시간 |
| 상태 문서 | 14시간 + **내용까지 틀림** |
| 기록용 빈 파일 2종 | 25시간째 0줄 |

**서브커맨드 60개 중 사용 흔적이 있는 것은 8개다.**

빈 칸이 빈 이유도 측정됐다. 같은 25시간 동안 사람은 세션 기록 5건·패턴 문서 6건·ADR 4건을 자발적으로 썼다. 기록 의지가 없어서 빈 게 아니라, **도구가 지정한 칸이 작업 흐름에 안 걸려서** 빈 것이다.

### 2-B. 정확성 결함 (같은 도그푸딩, 이슈 등록분)

| 이슈 | 심각도 | 내용 |
|---|---|---|
| #520 | high | `vhk check`가 "필수"로 선언한 토큰을 "금지" 패턴으로 뒤집어 읽는다. 단순 오탐이 아니라 **AI에게 안전장치를 삭제하라고 지시하는** 방향으로 작동한다 |

### 2-C. 구조 진단 (1차 도그푸딩 총평)

> 설계 축(RULES.md = 원본 → 전 도구 전파 → 검사로 차단) 중 **1번과 2번은 잘 작동한다. 3번(차단)이 비어 있다.** 규칙을 8개 썼는데 기계가 검사하는 건 1개다.

코드로도 확인된다.

| 확인 | 근거 |
|---|---|
| CI 필수 검사를 만들어주는 수단이 없다 | `src/`에 워크플로 템플릿 0건 |
| 자기 저장소도 작업 단위 검사를 CI에 안 걸었다 | `.github/workflows/ci.yml`이 주석으로 자인 |
| 커버리지 기준값이 없다 | vitest 임계 미설정, diff 커버리지는 경고만 |
| MCP 35개 도구 중 검증 계층 노출 0 | receipt·verify·review·goal·stats·mission 전부 미노출 |

### 2-D. 자율 에이전트 리서치 (2026-07-27, 7축·127인용 전수검증)

결정 6개가 확정됐다.

| # | 결정 |
|---|---|
| 1 | 검증 계층 노선 유지 — AI의 허위 완료 보고는 실재하며 실패의 45~76%를 차지. 교집합 지배자 없음 |
| 2 | 구현은 기존 계약 확장 — 권한 단계·위험도별 승인 규칙 먼저, 실행 상한은 PR까지 |
| 3 | 완주 5회 기준 유지 가능 — 단 결정론 3중 판정 + 롤링 강등 + 표본 점검이 짝일 때만 |
| 4 | 진화 후보 42건은 소비가 아니라 **정리**. 신규는 인라인 1클릭 + 만료. 큐 폐지, 자동 적용 금지 |
| 5 | 병목 입증은 계측 3종 신설 후 4주 실측 |
| 6 | 무인 실행 유지하되 경계 축소 — 머지 승인 6중 기준화, 비용 서킷브레이커 |

|---|---|
| 134 | UTF-8 BOM·LF·CRLF Goal body에서 코드 펜스 밖의 정확한 `### Phase N`과 `- [ ]`·`- [x]`·`- [X]` 뒤 `**Task N**` 문법만 읽힌다 · Phase와 Goal 전체 Task 번호는 각각 양수·고유·오름차순이며 결번을 허용하고 빈 Phase·Phase 밖 Task·중복·역순을 차단한다 · `[ ]`은 `pending`, `[x]`·`[X]`는 `completed`, Task 라벨 직후의 정확한 `` `(na)` ``는 `notApplicable`로 계산하고 `[x]`·`[X]`+`(na)`를 차단한다 · `completed`·`notApplicable`은 terminal, 첫 Phase pending은 ready, 이후 Phase pending은 직전 Phase Task 전부 terminal일 때만 ready이고 아니면 waiting이다 · 첫·같은 Phase `dependsOn`은 빈 배열이고 다음 Phase의 각 Task는 직전 Phase 모든 string Task ID에 의존한다 · `/ 증거:`·`/ evidence:` 값은 optional hint일 뿐 완료 증거가 아니다 · 4 Phase·11 Task 도그푸딩 fixture를 소비자 복사본 수정 없이 읽는다 |
| 135 | `vhk context --json`이 `schemaVersion`·`valid`·`activeGoal`·`warnings`·`errors`를 가진 `WorkContextV1` JSON 하나만 stdout에 출력하고 어떤 파일도 쓰지 않는다 · `activeGoal` 아래 `phases`와 평탄한 `tasks` 배열이 있고 각 Task는 `goal:N/task:N` string `id`, `goal:N/phase:N` string `phaseId`, `sourceStatus`·`readiness`·string[] `dependsOn`·`evidenceHint`·Goal source root 기준 상대 `sourceRef`·1-based `sourceLine`을 가진다 · Phase 없는 Goal은 빈 phases/tasks와 warning·exit 0으로 호환한다 · 구조 오류와 `--compact --json` 충돌은 `valid: false`인 원문 없는 JSON과 exit 1로 끝난다 · 시크릿·홈 절대경로·개인 식별자·실제 외부 객체 ID는 직렬화 전에 차단하고 입력 원문·절대경로·stack을 출력하지 않는다 · 기존 사람용 context·Goal 명령·선택 순서·MCP API는 불변이다 |
| 110 | 완주 집계가 자기 보고가 아니라 **검증 통과 + 검증 리포트 유효 + 사람 개입 0** 세 조건 전부일 때만 이뤄진다 · 작업 유형이 구분 기록된다 · 최근 10회 중 3회 실패 시 권한이 축소되고 그 전이가 기록된다 · 인프라 오류는 실패 집계에서 빠진다 |
| 111 | 사람 대기시간·내용 확인 없이 승인한 비율·상태 파악에 쓴 시간이 기록된다 · 폐기된 실행의 토큰 비용이 기록된다 · `vhk stats`에 병목 섹션이 생기고 표본 0이면 0이라고 정직하게 표시한다 |

**순서:** 134 → 135 → 110 → 111 직렬. Phase/Task projection과 안전한 JSON 표면을 먼저 고정한 뒤
그 실행 단위를 대상으로 완주와 병목을 계측한다.

**공통:** 110·111의 기존 기록 스키마에 추가되는 필드만 optional로 두어 기존 기록 파일과 하위호환한다. `WorkContextV1`과 Task 공개 필드는 135 수용 기준의 필수 계약이다.

### 6-4. 관찰 게이트

- 기간 4주와 유효 실행 10회를 모두 충족한다.
- 유효 실행은 작업 유형·최종 결과·현재 HEAD와 일치하는 verify 결과·사람 개입 여부가 기록되고 인프라 실패가 아닌 실행이다.
- 최근 10회 중 실패 3회 이상 또는 치명적 외부 부작용·안전 위반 1회 이상이면 다음 단계로 가지 않는다.
- 자동 승인하지 않는다. 사람이 신뢰도와 병목을 확인해 계속 또는 중단을 결정한다.
- 관찰 전에는 124·125도 제품 코드를 구현하지 않는다.
