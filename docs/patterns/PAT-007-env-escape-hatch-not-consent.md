패턴명: 대화형 탈출구 환경변수를 승인 신호로 오용
카테고리: state
증상: 위험 작업 가드가 비대화형 환경에서 잘 차단하다가, 터미널 호환용 환경변수(예: FORCE_INTERACTIVE=1)를 켜면 확인 프롬프트 없이 실행된다. 자동화 에이전트가 env 한 줄로 사람 승인 게이트를 통과한다.
원인: "프롬프트를 띄울 수 있는가"(feasibility)와 "사람이 승인했는가"(consent)를 하나의 대화형 판정 축으로 합쳤다. 탈출구 환경변수는 전자를 보정하는 장치인데, 승인 분기가 같은 판정을 재사용하면 env 값이 곧 y 응답이 된다.
해결: 두 축을 분리한다. 승인이 걸린 분기(confirm/warn)는 실제 TTY(stdin.isTTY)나 명시 플래그(--yes)만 인정하고, 탈출구 환경변수는 가드 밖의 일반 프롬프트 경로에만 적용한다. "탈출구 경로에서 진짜 프롬프트를 요구"하는 절충은 기각 — stdin 파이프 자동화에서 프롬프트가 행(unsettled await)으로 죽어 무출력 비정상 종료가 된다(실측 exit 13). 탈출구 사용자는 차단 안내가 알려주는 명시 플래그로 승인하게 한다.
적용조건: 대화형 감지에 우회용 환경변수가 있는 CLI/도구 + 사람 승인이 필요한 위험 작업 가드가 공존할 때. 특히 AI 에이전트가 환경변수를 세팅할 수 있는 실행 환경.

# 대화형 탈출구 환경변수를 승인 신호로 오용

## 사례 (vhk #611 3차 검증 라운드)

save 가드의 TTY 판정을 `isInteractive()`(stdin TTY + `VHK_FORCE_INTERACTIVE` 탈출구)로 "통일"하자, 완전 비대화형에서 `VHK_FORCE_INTERACTIVE=1 vhk save -m "msg"` 가 승인 플래그 0개로 커밋 + 원격 push까지 완주했다. 적대 검증이 실측으로 잡았고, 원장에는 `reason:'confirmed'` 로 남아 사람의 y/N 과 env 위조가 구분되지 않았다.

## 원칙

- **env ≠ consent.** 환경변수는 "프롬프트 렌더링이 가능하다"는 힌트일 뿐, 사람의 응답이 아니다.
- 승인은 셋 중 하나만: 실제 TTY 프롬프트 응답 · 명시 플래그(--yes, 또는 위험 요소가 빠진 축소 경로를 뜻하는 플래그 — vhk 의 --no-push 처럼 반출 0 이면 그 자체를 승인으로 인정 가능) · 상위 시스템의 서명된 승인.
- 탈출구 경로에서의 실프롬프트 절충은 자동화 stdin 에서 행이 되므로 금지 — 클린 차단 + 플래그 안내가 정답.
- 예외적으로 대화형이 *경험적으로 증명된* 경로(직전에 실제 프롬프트 응답을 받아낸 메뉴 등)만 명시 주입으로 통과시킬 수 있다.
