패턴명: 백업 브랜치가 이력 재작성을 무효화
카테고리: git
증상: 민감 정보를 지우려고 이력을 재작성했는데, 릴리스의 전체 이력 경계 검사(--all-refs)가 수십 건의 노출을 보고한다. 기본 브랜치 이력은 깨끗한데 검사만 실패한다.
원인: 재작성 전에 떠둔 백업 브랜치(backup/*)가 같은 공개 원격에 push되어 있으면, 지웠던 커밋·blob 전체가 그 ref 를 통해 계속 도달 가능하다. 재작성은 ref 가 가리키는 이력만 바꾸므로 다른 ref 가 옛 이력을 잡고 있으면 아무것도 지워지지 않은 것과 같다.
해결: ①재작성 전 백업은 공개 원격이 아니라 로컬 번들(git bundle create — 완전한 이력 보존·verify 가능)이나 사설 저장소로 뜬다 ②이미 노출됐다면 번들 백업 후 원격 브랜치 삭제(git push origin --delete) ③원인 특정은 원격을 건드리지 않고 로컬 remote-tracking ref 만 지워 재검사(git branch -rd → 검사 → git fetch 로 복원)하면 가역적으로 된다.
적용조건: 공개 저장소에서 이력 재작성(민감 정보 제거)을 수행하는 모든 프로젝트. 특히 자동화가 backup/* 브랜치를 만드는 워크플로.

# PAT-005: 백업 브랜치가 이력 재작성을 무효화

## 무슨 일이 있었나

vhk 는 2026-07-27 공개 경계 정리를 위해 main 이력을 재작성했다. 그 뒤 2026-08-04 자동
재정렬 작업이 `backup/pre-autopull-realign-20260804` 브랜치를 **같은 공개 원격에** push 했는데,
이 브랜치가 재작성 이전 이력(개인 운영 경로·이메일·로컬 원장)을 통째로 보존하고 있었다.

v2.14.0 릴리스 워크플로의 `--all-refs` 경계 검사가 21건의 노출로 실패하면서 발견됐다 —
기본 브랜치만 보는 일상 검사는 통과했고, 전체 ref 를 보는 릴리스 검사만 잡았다.

## 교훈

- **재작성 전 백업의 목적지가 공개 원격이면 재작성이 무효다.** 백업 의도(복구 가능성)와
  보존 위치(공개 여부)는 분리할 수 있다 — `git bundle` 은 완전한 이력을 파일 하나로 보존한다.
- **전체 ref 검사(--all-refs)는 릴리스 게이트에 있어야 잡힌다.** 일상 검사(HEAD 기준)로는
  다른 ref 의 노출이 보이지 않는다.
- **원인 특정은 가역적으로**: 원격 삭제 전에 로컬 remote-tracking ref 만 지우고 재검사하면
  어느 브랜치가 원인인지 원격 무변경으로 확정할 수 있다.
